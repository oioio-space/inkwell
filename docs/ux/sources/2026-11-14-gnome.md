## 1. Design principles (HIG)  https://developer.gnome.org/hig/principles.html

1. Design for People. "People are at the heart of GNOME design." Must work for different abilities, cultures, devices; no specialist knowledge.
2. Make it Simple. "The best apps do one thing and do it well." Target one context of use, reveal complexity gradually, keep common actions easy to reach.
3. Reduce User Effort. "If something can be done automatically, do it automatically." Fewer steps, less to remember.
4. Be Considerate. "Allow destructive actions to be undone instead of asking for confirmation." Anticipate errors, avoid interrupting people.

Implication for inkwell: undo (toast) beats confirmation dialogs; progressive disclosure beats dense toolbars.

## 2. HIG guidelines (cross-cutting)

### 2.1 Styling  https://developer.gnome.org/hig/guidelines/ui-styling.html
- No numbers on the page; it defers to libadwaita.
- Light is the default for most apps; dark default only for rich visual content (images, video). "Per-app style preferences are mainly useful for text editors and apps used for long periods" -> offer exactly three: light, dark, follow system.
- "Keep custom styling to a minimum." Use existing style classes and colour variables, which adapt to light/dark/high-contrast. "Don't use classes and variables outside their intended purpose."
- Never colour alone to distinguish information (add shape, position or text). Avoid flashing/blinking. Test high contrast.

### 2.2 Typography  https://developer.gnome.org/hig/guidelines/typography.html
- Default system font: Adwaita Sans ("a custom built variant of Inter"). "Don't hard-code font styles or sizes"; "express font-sizes as relative values"; "minimize the number of font sizes and weights".
- Standard text styles: body, heading, caption, caption-heading, title-1..4 (large-title deprecated).
- "Avoid italic or oblique faces." "Do not use all caps." No text over graphical backgrounds/textures.
- Typographic characters: ellipsis U+2026, curly quotes U+201C/U+201D, apostrophe U+2019, multiplication sign U+00D7, bullet U+2022, en dash U+2013 for ranges, narrow no-break space U+202F before units.

### 2.3 Writing style  https://developer.gnome.org/hig/guidelines/writing-style.html
- "User interface text should be short and to the point." Neutral tone, avoid "you"/"my" ("Your Records" if ownership needed). US English source text. No sentences built from several controls. No "i.e."/"e.g.".
- Header capitalisation: headings, header bars, tab/view titles, buttons, switches, menu labels, tooltips. (Capitalise words >= 4 letters, all verbs, nouns, first and last word.) Example "Document Cannot Be Found".
- Sentence capitalisation: check boxes, radio buttons, sliders, text entries, field/combo labels, explanatory text in dialogs and notifications.
- Headings are not sentences ("Three Documents Updated"); informal sentence-style headings allowed with sentence case + bold.
- Ellipsis "…" when more input or confirmation is needed before the action runs ("Save As…", "Delete…"); not on "Properties"/"Preferences".
- "Text generally shouldn't end with a period."

### 2.4 Keyboard  https://developer.gnome.org/hig/guidelines/keyboard.html
- Use standard shortcuts for matching functions. Ctrl+letter for custom; Shift+Ctrl+letter for the reverse/extension of another function. **No Alt** in shortcuts (conflicts with access keys), **no Super**.
- Every labelled control gets an Alt access key (first letter, avoid thin/descender letters, translated with the string).
- "every action should also be possible with the keyboard." Logical focus order; label immediately before its control; arrows for directional movement; test keyboard-only.
- Navigation keys: Tab/Shift+Tab; Ctrl+Tab in text entries; Return activates; Space toggles; F10 opens primary/secondary menu; Menu or Shift+F10 context menu; Esc closes transient containers.

### 2.5 Standard shortcut reference  https://developer.gnome.org/hig/reference/keyboard.html (verified tables)
- Basic: Close Ctrl+W; Quit Ctrl+Q; Help F1; Side Pane F9; Menu F10; Keyboard Shortcuts Ctrl+?; Preferences Ctrl+,
- Files: New Ctrl+N; Open Ctrl+O; Save Ctrl+S; Save As Shift+Ctrl+S; Print Ctrl+P; Print Preview Shift+Ctrl+P; Send Ctrl+M; Properties Alt+Return
- Editing: Undo Ctrl+Z; Redo Shift+Ctrl+Z; Cut/Copy/Paste Ctrl+X/C/V; Paste Special Shift+Ctrl+V; Duplicate Ctrl+U; Select All Ctrl+A; Deselect All Shift+Ctrl+A; Find Ctrl+F; Find Next Ctrl+G; Find Previous Shift+Ctrl+G; Replace Ctrl+H
- View: Zoom In Ctrl++; Zoom Out Ctrl+-; Normal Size Ctrl+0; Reload Ctrl+R
- Formatting: Bold Ctrl+B; Italic Ctrl+I; Underline Ctrl+U (note Ctrl+U is also Duplicate in the table; the HIG lists both)
- Bookmark: Add Ctrl+D; Edit Ctrl+Alt+D
- Navigation: Back Alt+Left; Forward Alt+Right; Up Alt+Up; Home Alt+Home; Enter Location Ctrl+L; PageUp/PageDown; First/Last page Ctrl+Home/Ctrl+End
- Reserved legacy (avoid): Alt+Tab (+Shift, +`), Alt+F4, Alt+F6, Alt+F7, Alt+F8, Alt+F5, Ctrl+Alt+Tab, Alt+Space, Ctrl+Alt+Delete.
- Tabs (https://developer.gnome.org/hig/patterns/nav/tabs.html): Ctrl+T new, Ctrl+W close, Ctrl+PageUp/PageDown switch, Ctrl+Home/End first/last, Ctrl+Tab, Alt+1-9.
- Inkwell mapping: sidebar toggle F9, preview toggle should avoid Alt; history/version panel and share need non-reserved Ctrl/Shift+Ctrl combos.

### 2.6 Pointer & touch  https://developer.gnome.org/hig/guidelines/pointer-touch.html
- NO numeric target size in the HIG ("large enough to be comfortably used with different pointing devices"). (Numbers come from libadwaita CSS, see 3.3.)
- Avoid double-click and chording. Don't rely on hover to reveal essential actions/information. Every pointer action must work from keyboard. Don't name devices in UI text.
- Secondary action = context menu; not for alternatives like delete. Provide menu only when there is a relevant set. No middle-button actions. Esc cancels in-progress pointer operations (drag, draw).
- Three/four-finger gestures and top/bottom edge drags reserved for the system.

### 2.7 Adaptive  https://developer.gnome.org/hig/guidelines/adaptive.html
- Smallest recommended desktop display **1024x600**, "this size should be supported by all apps". Phone-capable apps scale to **360x294**.
- Design from the most constrained environment up. Avoid many small panes ("hard to make adaptive"). Use list patterns that "scale well to both very narrow and very wide view widths".
- Sidebars never excessively wide/narrow vs. the main area. Use breakpoints (e.g. utility pane moves to bottom panel). Resizing must be smooth; "Widgets should not jump around or vanish without an animation." Limit content width at large sizes (max-width containers). Don't infer capabilities from form factor.

### 2.8 Navigation  https://developer.gnome.org/hig/guidelines/navigation.html
- "Ensure that the amount of content in each view is easy to digest: don't pack too much in." "Each view should have a clear focus or subject." "Avoid deeply nested hierarchies ... one level of depth." Don't mix navigation types non-standardly. Prefer views inside the window over new windows. Few equivalent pages -> view switcher; too many -> sidebar.

### 2.9 UI icons  https://developer.gnome.org/hig/guidelines/ui-icons.html
- Symbolic icons drawn at **16x16**; "Avoid other sizes to prevent fuzzy rendering". Display sizes 32, 64, 128. Monochrome SVG, 2px strokes (avoid 1px), pixel-grid aligned, recolourable.
- "Identify a control with either a label or an icon, not both" (exceptions: sidebars, view switchers; header bar icon+label also allowed, see 4.1). Use an icon only if recognisable, else a label. Reuse existing GTK/Icon Dev Kit icons.

### 2.10 App naming  https://developer.gnome.org/hig/guidelines/app-naming.html
- One or two simple nouns, under 15 characters, header capitalisation; avoid "G" prefix, puns, invented words, trademarks, acronyms.

### 2.11 Accessibility  https://developer.gnome.org/hig/guidelines/accessibility.html
- No numeric contrast ratios on the page. Every element needs a short descriptive accessible name.
- Test checklist: high contrast, large text, keyboard only, screen reader (Orca) with display off, on-screen keyboard.

### 3.4 Animation (libadwaita C sources, verified lines)
- AdwTimedAnimation: default `duration` is 0 (caller must set); default easing `ADW_EASE_OUT_CUBIC`. Docs give no recommended durations. https://gitlab.gnome.org/GNOME/libadwaita/-/raw/main/src/adw-timed-animation.c
- 1.7 added cubic-bezier easings `ADW_EASE`, `ADW_EASE_IN`, `ADW_EASE_OUT`, `ADW_EASE_IN_OUT` (https://release.gnome.org/48/developers/). Their bezier control points: UNVERIFIED (not fetched).
- AdwSpringAnimation: default epsilon 0.001; springs have no fixed duration (estimated-duration property). Damping ratio: 0 undamped, <1 underdamped, 1 critical (fastest, no overshoot), >1 overdamped. https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.10/struct.SpringParams.html
- Springs actually used (source): NavigationView page transition `adw_spring_params_new (1, 1, 1000)`; OverlaySplitView sidebar `adw_spring_params_new (1, 0.5, 500)`. Argument order is (damping_ratio, mass, stiffness) per the C source usage; the docs page summary lists "mass, stiffness and damping_ratio", so the order is UNVERIFIED on the docs page. Both use damping ratio 1 = critically damped, no bounce; both give the same natural frequency sqrt(stiffness/mass) = about 31.6 rad/s (my arithmetic, not a doc statement), i.e. the same speed of motion. Takeaway: GNOME navigation motion is critically damped springs, no overshoot, interruptible, velocity-preserving on swipe.
- Toast default timeout **5 seconds** (0 = until dismissed). https://gitlab.gnome.org/GNOME/libadwaita/-/raw/main/src/adw-toast.c
- Dialog: bottom sheet when `max-width: 450px` or `max-height: 360px`, else floating centred; floating dialog min natural width for sheet 360. https://gitlab.gnome.org/GNOME/libadwaita/-/raw/main/src/adw-dialog.c
- Reduced motion: GNOME 50 added a system Reduced Motion setting (Settings > Accessibility > Seeing). GTK exposes CSS media query `(prefers-reduced-motion: reduce)`; libadwaita 1.9 widgets honour it. Guidance: swap in gentler alternative animations, do not just remove all animation ("alternative animations that do not induce discomfort or distraction"). https://thisweek.gnome.org/posts/2025/11/twig-224/ , https://release.gnome.org/50/ , https://release.gnome.org/50/developers/
  - Webview equivalent: `@media (prefers-reduced-motion: reduce)` replace slides/springs by short cross-fades; keep progress indicators moving gently.

## 4. Patterns (HIG)

### 4.1 Header bars  https://developer.gnome.org/hig/patterns/containers/header-bars.html
- Three alignment points: start (left in LTR), centre, end. Main actions (new, add, open, back) at start; heading (or view switcher) in centre; "Menus typically go at the end."
- "Keep the number of controls small" so the window can shrink. Update controls when views/modes change. "Always ensure that there is some blank space in the header bar to allow it to be dragged."
- Every primary header bar control has a tooltip.
- Buttons: no visible background/border where possible (icon-only, icon+label, split buttons are flat automatically). **Avoid in primary header bars**: label-only buttons, suggested/destructive buttons, linked buttons. Add icons to label-only buttons; use spacing (or `.spacer` separators) rather than linked groups. Action dialogs may keep label-only buttons.

### 4.2 Windows  https://developer.gnome.org/hig/patterns/containers/windows.html
- Primary windows independent and resizable; secondary windows belong to a primary one, typically modal; avoid stacking secondaries; they should not be larger than the parent. Ctrl+W closes; modal windows also close with Esc. Restore previous window size on restart.

### 4.3 Sidebars  https://developer.gnome.org/hig/patterns/nav/sidebars.html
- Use when there are more views than a view switcher holds, or for dynamic locations / frequent switching. "Sidebars should be avoided for apps which provide rich or immersive content."
- Order by usefulness; most recently updated at top for dynamic lists. "Header bar controls which affect the sidebar list should be placed above the list." Keep key information visible in multi-line rows. API: AdwNavigationSplitView.

### 4.4 Utility panes  https://developer.gnome.org/hig/patterns/containers/utility-panes.html
- Left if it affects the main view; right if subordinate. May be permanent or transient. "Unlike sidebars, utility panes do not intersect the header bar." Must overlap the main view when width is short. Toggle shortcut **F9**. API: AdwOverlaySplitView.
- Real example: GNOME Text Editor document-properties pane is a 300px panel on the right, toggled with F9 (editor-window.ui, verified).
- Inkwell fit: the live preview is a content pane (not a utility pane); people/history/comments are right-hand utility panes, F9 toggle.

### 4.5 View switchers  https://developer.gnome.org/hig/patterns/nav/view-switchers.html
- 3 to 5 views; more -> sidebar. Header capitalisation, nouns, similar lengths. Switch to bottom bar when narrow (550sp, see 3.5). Don't make one view's controls affect other views.

### 4.6 Menus  https://developer.gnome.org/hig/patterns/controls/menus.html
- Primary menu: standard group at the end, in order **Preferences, Keyboard Shortcuts, Help, About <App Name>**. Preferences/Shortcuts only if present. About is required. **No Close or Quit** in the primary menu.
- Icon `open-menu-symbolic`, tooltip/a11y label "Main Menu". At the end of the header bar; with a sidebar it goes above the sidebar list; with hierarchical navigation only on the top-level view.
- 3 to 12 items per menu, submenus 3 to 6, **no nested submenus**. Group similar items; do not mix actions, checkboxes, radios in a group. Verbs for commands, adjectives for settings, header capitalisation; label-swap (Play/Pause) only for obvious opposites, never for settings. Every item has an access key; secondary menus don't repeat Preferences/About.
- Real example, GNOME Text Editor primary menu: theme and zoom controls; New Window; Show Open Tabs; Save / Save As… / Discard Changes…; Find/Replace…; Print…; Fullscreen; then Preferences, Keyboard Shortcuts, About Text Editor.

### 4.7 Popovers  https://developer.gnome.org/hig/patterns/containers/popovers.html
- Avoid many control types, group same-type controls, optional heading if purpose unclear. "Close or Done buttons are not usually required." Keep small: "not cover more than a third of their parent window". Low complexity. Esc closes.

### 4.8 Buttons  https://developer.gnome.org/hig/patterns/controls/buttons.html
- Outside header bars: "buttons should contain either an icon or a label, and not both". Labels: imperative verbs, header capitalisation, short; adjacent buttons same width.
- "Each view should only ever include a single button using either the suggested or destructive styles."

### 4.9 Dialogs  https://developer.gnome.org/hig/patterns/feedback/dialogs.html
- Two types: alert (1-3 buttons; message or question) and action (options before an action). Both are modal and need a response.
- Destructive actions need confirmation or undo; "undo is typically a better option than a confirmation dialog". Error dialogs "should be avoided where possible" -> toast for non-critical errors.
- Action dialog: header bar, heading, a specific imperative affirmative label ("Save", not "OK"/"Done"); keep it insensitive until options are chosen; never show unexpectedly; give initial focus to the first-used control.
- Button order: **cancel first (left), affirmative after**. Return activates the affirmative default unless the action is irreversible/destructive (then no default). Esc = cancel.
- AdwAlertDialog (since 1.5): heading, body, optional child, responses with unique IDs, `default-response`, `close-response`, suggested/destructive appearance, horizontal or vertical button layout; closes automatically on response. https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.10/class.AlertDialog.html

### 4.10 Toasts  https://developer.gnome.org/hig/patterns/feedback/toasts.html
- "always transient and user dismissible", brief title (informal heading style), at most one button and only if directly relevant (e.g. Undo), bottom-centre of the window, not over a specific area. For ongoing state use banners; for out-of-app messages use notifications. Default timeout 5s (3.4).

### 4.11 Banners  https://developer.gnome.org/hig/patterns/feedback/banners.html
- Persistent states only ("Working offline", "Unlock to change settings"). One short title, informal heading style, no lengthy explanations, never auto-hide, only for important info.

### 4.12 Placeholders / empty states  https://developer.gnome.org/hig/patterns/feedback/placeholders.html
- Heading that "communicates the empty state and provides guidance", optional description ("Use the + button to add items"), relevant action controls with suggested style. Illustration style only for an app's initial empty main view; symbolic style (subtle, neutral) for ordinarily-filled spaces (empty folders, search results). `.compact` StatusPage for sidebars/popovers.

### 4.13 Boxed lists  https://developer.gnome.org/hig/patterns/containers/boxed-lists.html
- For "relatively small static lists" (large/dynamic -> list views). Semantic sections with optional headings. Navigation rows end with `go-next-symbolic`. Rows have one control, never more than two; clicking the row background triggers the control; controls focusable, row not. Differentiate text by size, weight, colour; symbolic icons; min/max width. Add button at top or an add button row at end; remove at the end of each row; drag handles at start for reorder (menu move up/down required for a11y). Pill button for a single standalone action; button rows otherwise; ellipsis replaced by a trailing arrow when a button row opens a new view.
- libadwaita rows: ActionRow, SwitchRow, ExpanderRow, ComboRow, EntryRow, PasswordEntryRow, SpinRow, `.property` rows, ButtonRow, PreferencesGroup. https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.10/boxed-lists.html

### 4.14 Lists & column views  https://developer.gnome.org/hig/patterns/containers/list-column-views.html
- "Keep list rows simple and regular. Most should only contain one or two elements each." Symbolic icons. Sort arrow in column header: down = natural order, up = reverse. Min/max widths.

### 4.15 Search  https://developer.gnome.org/hig/patterns/nav/search.html
- Search bar slides below the header bar, hidden until activated (type-to-search, Ctrl+F, header search toggle). Always-visible only if search is core. Live results, fast, incremental; empty state "No results"; global; typo-tolerant; most relevant first. "it should not be relied on exclusively."

### 4.16 Progress, spinners  https://developer.gnome.org/hig/patterns/feedback/spinners.html , .../progress-bars.html
- Indicate progress when an operation takes more than around **3 seconds**; under that, none. Spinners for shorter tasks; progress bar if more than **30 seconds**. Delay showing variable-length spinners; place near the thing it relates to; only one spinner at a time.
- Progress bars: text label of what is done ("13 of 19 images rotated"), time estimates marked "About 3 minutes left", avoid activity mode, inline not in progress windows, pause/cancel for heavy operations, thin bars at the bottom of the header bar for background progress.
- AdwSpinner (since 1.6): never smaller than 16x16 and never larger than 64x64.

### 4.17 Tooltips  https://developer.gnome.org/hig/patterns/feedback/tooltips.html
- All primary header bar controls get tooltips; elsewhere only if really useful; never the only carrier of critical info; if one control in a container has one, all do; header capitalisation; don't repeat a visible label. Standard texts: Back, Search, Main Menu, Menu (e.g. "Document Menu"), New Tab, Bookmarks.

### 4.18 Switches, text fields  https://developer.gnome.org/hig/patterns/controls/switches.html , .../text-fields.html
- Switches preferred over check boxes for clear on/off, labelled with nouns in header caps, insensitive when unavailable.
- Text fields need placeholder or label; action placeholder phrased "Search for a city…"; apply settings on Return or focus loss; show positive validation feedback in real time rather than negative errors while typing; password fields use the dedicated control with reveal.

### 4.19 Notifications, selection mode, overlaid controls
- Notifications https://developer.gnome.org/hig/patterns/feedback/notifications.html : only for events relevant outside the app; title header caps, optional one-sentence body, max 3 actions, never the only way to do something; remove invalid ones.
- Selection mode https://developer.gnome.org/hig/patterns/containers/selection-mode.html : only for large collections and at least three actions on selection; cancel in header, count in heading, actions in bottom action bar.
- Overlaid controls https://developer.gnome.org/hig/patterns/controls/overlaid.html : show on pointer move/tap; don't use if they obscure relevant content (e.g. effects of image edits).

## 6. libadwaita widgets, one line each ("when to use")

All 1.10 docs under https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.10/class.<Name>.html

- AdwToolbarView (1.4): wraps one content page with top/bottom bars; bars flat by default with a subtle undershoot shadow when content scrolls; set `raised` for utility panes/tab views whose pages have different backgrounds; `extend-content-to-top-edge` lets content run behind bars. Replaces header `.flat`.
- AdwHeaderBar: window/dialog top bar; a bar inside a dialog shows title and close button.
- AdwNavigationSplitView (1.4): sidebar + content that collapses into an AdwNavigationView at a breakpoint (typical 400sp); default 25% / 180sp / 280sp; sidebar can go at the end (1.7).
- AdwOverlaySplitView (1.4): sidebar overlays content when collapsed; use for utility panes and Nautilus-style places sidebars; same default sizing.
- AdwNavigationView (1.4): stack of pages with back navigation (spring transition, 3.4).
- AdwBreakpoint (1.4): size condition with setters (properties set while applied); works in windows, dialogs, AdwBreakpointBin. Condition example `max-width: 400px`; the `sp` unit is used in the adaptive doc (doc page for Breakpoint does not mention sp: UNVERIFIED there).
- AdwDialog (1.5): adaptive modal in-window dialog; centred floating window, or bottom sheet at max-width 450px / max-height 360px; not resizable; size via content-width/height, `follows-content-size`; never larger than parent; swipe down to dismiss as a sheet.
- AdwAlertDialog (1.5): message/question with responses (see 4.9).
- AdwPreferencesDialog / PreferencesPage / PreferencesGroup: standard preferences (boxed-list groups, search built in).
- AdwBottomSheet (1.6): persistent bottom bar that opens into a sheet integrated with the layout (music-player style); for transient sheets use AdwDialog; not adaptive by itself.
- AdwMultiLayoutView (1.6): moves children between named layouts at a breakpoint (e.g. sidebar becomes bottom sheet at 400sp).
- AdwSpinner (1.6): loading spinner, 16-64px; AdwSpinnerPaintable for status pages.
- AdwButtonRow (1.6): list row that is a button, for actions at the end of a boxed list.
- AdwToggleGroup / AdwToggle (1.7): exclusive icon/label toggles; "mostly useful for icon-only toggles"; `.flat`, `.round`; radio-group accessibility role; give toggles tooltips.
- AdwInlineViewSwitcher (1.7): view switcher built on a toggle group, display-mode icon/label/both; use for compact in-content switching (e.g. Source/Preview/Split).
- AdwWrapBox (1.7): box that wraps lines (tag lists, avatars of people); child-spacing and line-spacing properties (6/6 in the adaptive example).
- AdwShortcutsDialog / ShortcutsSection / ShortcutsItem / ShortcutLabel (1.8): adaptive shortcuts window with search, replaces GtkShortcutsWindow; sections of items (title, accelerator, optional LTR/RTL).
- AdwSidebar (1.9; prefix/suffix slots 1.10): sections, items, filter, tooltips, context menus, drop target, empty-state `placeholder`, `mode` sidebar or boxed-list page when collapsed, exactly zero-or-one selected item.
- AdwViewSwitcherSidebar (1.9): sidebar that controls an AdwViewStack with sections, icon + label + unread dot/badge; replaces GtkStackSidebar.
- AdwViewSwitcher / ViewSwitcherBar / ViewSwitcherTitle: top and bottom view switchers (3-5 views).
- AdwStatusPage: empty/error states; `.compact` for sidebars and popovers.
- AdwBanner: persistent state strip; 1.7 added a prominent action button option.
- AdwToastOverlay / AdwToast: transient notices (5s default).
- AdwSplitButton: primary action plus dropdown; only suggested/destructive/flat/raised allowed, not pill.
- AdwTabView / TabBar / TabOverview / TabButton: tabs; overview shown at 500px (adaptive doc).
- AdwClamp / ClampLayout / ClampScrollable: maximum content width while shrinking.
- AdwAvatar: person avatar (initials/colour fallback); relevant for presence. (Doc page not fetched: usage details UNVERIFIED.)
- AdwSpringAnimation / TimedAnimation: see 3.4. Motion respects `Adw.get_enable_animations()` and the reduced-motion setting.

## 10. Rules most likely to change a webview-reimplemented app (shortlist, with section refs)

1. Header bar hygiene (4.1, 4.8): no label-only, suggested, destructive or linked buttons in the primary header bar; icon-only flat buttons spaced 6px, tooltips on all, empty draggable space, one primary menu at the end with the exact order Preferences / Keyboard Shortcuts / Help / About and no Quit.
2. One suggested/destructive button per view, undo toast instead of confirmation dialogs, specific verb labels, Cancel left of the affirmative, no default on destructive dialogs (4.8, 4.9, 4.10, principle 4).
3. Sidebar and panes (3.5, 4.3, 4.4): sidebar 25%/180-280sp with neutral (non-accent) 36px rows at 9px radius; utility panes (people, history) on the right, F9 toggle, overlay when narrow; breakpoints 400/550/682sp; support 1024x600 minimum.
4. Numbers to copy (3.1-3.3): window/dialog/popover radius 15px, card 12px, button/entry/menu 9px, controls 34px tall, header 47px, focus ring 2px inside, 200ms transitions with ease-out-quad, dim 55%, border 15% of currentColor, colour tokens for light and dark including sidebar/headerbar/popover/dialog surfaces; accent via a single variable following the system accent.
5. Motion and accessibility (3.4, 2.4, 2.11, 8): critically damped springs, `prefers-reduced-motion` replaces slides with gentle fades, never colour alone, full keyboard operation with standard shortcuts (no Alt/Super), high-contrast and large-text modes, icon buttons need accessible names, no hover-only actions.
