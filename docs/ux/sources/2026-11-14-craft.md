# UX craft sources for inkwell (non-GNOME): Apple HIG, UX science, best-in-class tools, local-first/P2P

Researched 2026-11-14. Convention: **[V]** = read on a fetched page this session (Apple pages were read through
Apple's own JSON endpoint `https://developer.apple.com/tutorials/data/design/human-interface-guidelines/<slug>.json`,
because the HTML pages are JS-only and WebFetch returns only the title; the text is Apple's, exact).
**[S]** = seen only in a search snippet / secondary source. **[U]** = unverified (from memory or page not readable) - do not quote.
Quotes are <= 25 words. "Apple HIG" URL pattern: https://developer.apple.com/design/human-interface-guidelines/<slug>

## 0. Findings with the strongest evidence that would most change an app like inkwell (read first)

1. **Status goes in place, not in alerts or spinners.** Apple Feedback: passive status near the thing it describes; interrupt only for
   data loss. Ink & Switch: P2P is "never fully online or offline", so a binary online/offline badge is wrong. -> one calm,
   per-document "saved on this device / synced with N people / waiting for X" line, never a modal. (sections 1.14, 5)
2. **Response budget is a hard numeric spec**: 0.1 s feels instant, 1 s keeps flow, 10 s loses attention (NN/g); RAIL: finish input
   transitions within 100 ms; animation 100-500 ms, ease-out, shorter for frequent actions (NN/g). Skeleton/spinner only after
   ~1 s; nothing under 1 s. -> measurable acceptance criteria for typing, preview refresh, sidebar, popovers. (sections 2, 3)
3. **Collaboration UI should be three things only**: a Share button in the toolbar with a one-line permission summary, a
   collaboration button/popover next to it (people list on top, at most a few custom items, "manage" at bottom), and
   colour-coded presence with follow mode (Zed/Figma spotlight). Apple says "offer only the most essential items". (1.12, 4)
4. **Fewer, deliberate chrome elements**: Apple Toolbars (avoid overflow by default, reduce backgrounds and tints, hide on demand with
   a reliable way back), Sidebars (<= 2 levels, never hidden by default), Linear (reduce noise, align labels/icons). Chrome
   neutral and monochrome; colour reserved for content, accent and presence. (1.3, 1.4, 4.7)
5. **Trust UX must be verified by the user, but short**: Signal-style numeric fingerprints get slower and *less* safe when longer
   (1 line: 13.2 % missed near-matches; 3 lines: 43.5 %; 162 participants). -> for peer invitation use a short, QR/shared-secret
   or short-code comparison, keep fingerprints as an advanced detail. (section 5)

## 1. Apple Human Interface Guidelines (HIG)

### 1.1 Stated principles (current wording)
- **Hierarchy, harmony, consistency** are the three principles of the current (2025 "Liquid Glass") design language.
  Evidence is secondary: WWDC25 session 356 notes [V] say "Don't rely on (color) decoration, but on grouping and layout" (hierarchy),
  "shapes with consistent curvature, size, and proportions create a unified rhythm" (harmony), "One layout, hierarchy or interaction
  should carry across every device" (consistency). The Apple session page itself returned no text, so the wording is from
  wwdcnotes. https://wwdcnotes.com/documentation/wwdc25-356-get-to-know-the-new-design-system/ and
  https://www.createwithswift.com/liquid-glass-redefining-design-through-hierarchy-harmony-and-consistency/ [S]
- Older trio *clarity, deference, depth* (iOS 7 era): [U] - not re-read on an Apple page this session; use only as history.
- Why it works for inkwell: "hierarchy by grouping and layout, not decoration" is directly actionable for an Adwaita-style UI
  where decoration is already minimal; "harmony" = concentric corner radii (outer radius = inner radius + padding) from the
  same WWDC notes [V]. Toolbar rule from the HIG [V]: "By default, standard buttons ... have corner radii that are concentric
  with bar corners."
- Mac-specific principles, "Designing for macOS" [V] https://developer.apple.com/design/human-interface-guidelines/designing-for-macos :
  - "Leverage large displays to present more content in fewer nested levels and with less need for modality."
  - "Let people resize, hide, show, and move your windows ... and support full-screen mode to offer a distraction-free context."
  - "Use the menu bar to give people easy access to all the commands they need."
  - "Handle keyboard shortcuts to help people accelerate actions and use keyboard-only work styles."
  - "Allow for personalization, letting people customize toolbars, configure windows ..., and choose the colors and fonts."
  - Interactions "can last anywhere from a few minutes ... to several hours of deep concentration": design for both.

### 1.2 Layout and spacing [V] https://developer.apple.com/design/human-interface-guidelines/layout
- "Align elements to make them easier to scan, and use indentation to convey hierarchy." Aligned items are read as related,
  indented items as subordinate.
- "Group related items ... you might use negative space, container shapes, or separator lines."
- Layout guides "restrict the width of text for optimal readability" (system margins/readable guides exist; HIG gives no
  character count). Resize: respect minimum/maximum window sizes but "don't use minimum and maximum sizes as a way to prevent resizing".
- "Don't change your app's functionality based on the space it occupies" (only how much is visible). Relevant to a narrow
  window: hide the preview pane, do not remove features.
- Spacing numbers exist only in platform-specific parts (visionOS "centers at least 60 points apart"; Accessibility: "about
  12 points of padding around elements that include a bezel", "about 24 points" around non-bezel elements [V]).
  No Apple-stated 4/8 pt grid was found on the pages read [U]; the 8-pt grid is industry convention (section 2.6).

### 1.3 Toolbars [V] https://developer.apple.com/design/human-interface-guidelines/toolbars
- "Choose items deliberately to avoid overcrowding." "Avoid layouts that cause toolbar items to overflow by default." The system adds
  the overflow menu; do not add one manually.
- "Reduce the use of toolbar backgrounds and tinted controls ... use the content layer to inform the color and appearance."
- "Consider temporarily hiding toolbars for a distraction-free experience ... offer ways to reliably restore hidden interface
  elements." (-> focus mode must have an obvious, always-reachable way out.)
- "Consider letting people customize the toolbar to include their most common items" (Mac), especially for long-use apps.
- WWDC25 notes [V]: "Remove unnecessary bar actions and move secondary actions into a menu"; "Group bar items by function and
  frequency"; "Don't group symbols with text"; primary action (Done) separate and tinted.
- Provide a useful window title that "helps people confirm their location" and tells windows apart.

### 1.4 Sidebars [V] https://developer.apple.com/design/human-interface-guidelines/sidebars
- "In general, show no more than two levels of hierarchy in a sidebar." Deeper -> split view with a content list.
- "Consider letting people hide the sidebar ... Avoid hiding the sidebar by default to ensure that it remains discoverable."
- "Group hierarchy with disclosure controls if your app has a lot of content."
- Icons take the system accent colour; fixed colours only when they clarify meaning ("VIP icon in Mail uses a yellow").
- Same two-level cap as NN/g progressive disclosure (section 2.1).
- Inspectors page: https://developer.apple.com/design/human-interface-guidelines/inspectors returned 404 on the JSON endpoint [U];
  Apple Sheets page [V] says to "Use a nonmodal view when you want to present supplementary items that affect the main task",
  naming a panel in macOS - the HIG-sanctioned pattern for a properties/history side panel.

### 1.5 Popovers and sheets
- Popovers [V] https://developer.apple.com/design/human-interface-guidelines/popovers :
  - "Use a popover to expose a small amount of information or functionality" (a few related tasks).
  - "Always save work when automatically closing a nonmodal popover. ... Discard people's work only when they click ... an explicit Cancel button."
  - "Show one popover at a time. ... Never show a cascade or hierarchy of popovers."
  - "Avoid using a popover to show a warning. ... use an alert instead."
  - Let people move from one popover to another with a single click; animate size changes.
- Sheets [V] https://developer.apple.com/design/human-interface-guidelines/sheets : in macOS a sheet is always modal;
  "Display only one sheet at a time"; "If you provide a Done button, always pair it with a Cancel button ... or a Back button";
  for self-contained or prolonged tasks "open a new window" rather than a sheet.

### 1.6 Alerts and writing [V]
- Alerts https://developer.apple.com/design/human-interface-guidelines/alerts :
  - "Use alerts sparingly." "Avoid using an alert merely to provide information." (Mail example: show an inline indicator.)
  - "Avoid displaying alerts for common, undoable actions, even when they're destructive." Alert only when uncommon + not undoable.
  - "Avoid showing an alert when your app starts."
  - Title "clearly and succinctly describes the situation"; never "Error" or "Error 329347 occurred"; up to three buttons; avoid
    titles that wrap past two lines; "Avoid explaining alert buttons."
- Writing https://developer.apple.com/design/human-interface-guidelines/writing :
  - "Write clear error messages ... display it as close to the problem as possible, avoid blame, and be clear about what someone can do."
  - "When labeling buttons and links, it's almost always best to use a verb." "Use possessive pronouns sparingly" ("Favorites" not
    "Your Favorites"). "Choose simple, plain language ... avoiding jargon" (matches inkwell's "personne" not "pair").
  - Example of a good error from the page: "Choose a password with at least 8 characters" beats "That password is too short".

### 1.7 Onboarding, launching, loading [V]
- Onboarding https://developer.apple.com/design/human-interface-guidelines/onboarding : "Ideally, people can understand your app ...
  simply by experiencing it, but if onboarding is necessary, design a flow that's fast, fun, and optional."
  "Teach through interactivity"; "Consider providing a collection of context-specific tips instead of a single onboarding flow";
  "Postpone nonessential setup flows or customization steps. Provide reasonable default settings."
- Launching https://developer.apple.com/design/human-interface-guidelines/launching : "Launch instantly."
  "Restore the previous state when your app restarts ... scroll the view to people's most recent position, and display windows in the
  same state and location in which people left them."
- Loading https://developer.apple.com/design/human-interface-guidelines/loading : "Show something as soon as possible" (placeholders
  replaced as content arrives); "Let people do other things ... while they wait"; determinate indicator when duration is known,
  indeterminate otherwise.

### 1.8 Feedback, undo [V]
- Feedback https://developer.apple.com/design/human-interface-guidelines/feedback : "The most effective feedback tends to match
  the significance of the information to the way it's delivered." Status passively, warnings interruptively.
  "Make sure all feedback is accessible" (colour + text + sound). "Warn people when they initiate a task that can cause data loss
  that's unexpected and irreversible. In contrast, don't warn ... when data loss is the expected result." "Show people when a command
  can't be carried out and help them understand why."
- Undo and redo https://developer.apple.com/design/human-interface-guidelines/undo-and-redo : "Help people predict the results"
  (menu labels "Undo Typing", "Redo Bold"); "Show the results of an undo or redo" (scroll the restored paragraph into view);
  "Let people undo multiple times ... Avoid placing unnecessary limits"; offer revert-all-since-open.
  -> for a CRDT editor: per-user undo must scroll to and flash the affected range, even if a peer edited nearby.

### 1.9 Drag and drop, keyboard, menus, search [V]
- Drag and drop https://developer.apple.com/design/human-interface-guidelines/drag-and-drop : "support drag and drop throughout your app";
  "Prefer letting people undo a drag-and-drop operation"; dropping within one container moves, across containers copies;
  drag image can preview the result. (files sidebar, images into the editor)
- Keyboards https://developer.apple.com/design/human-interface-guidelines/keyboards : "Respect standard keyboard shortcuts";
  "In general, don't repurpose standard keyboard shortcuts"; "Define custom keyboard shortcuts for only the most frequently used
  app-specific commands ... too many ... can make your app seem difficult to learn"; modifier order Control, Option, Shift, Command.
  Accessibility page: "Let people use the keyboard alone to navigate and interact."
- Menus https://developer.apple.com/design/human-interface-guidelines/menus : item labels are verbs; title-style capitalisation;
  drop articles; a toggled item can show the current state, add a verb when ambiguous ("Turn HDR On"). Menu bar = complete
  command list (= command palette's data source, section 4.1).
- Searching https://developer.apple.com/design/human-interface-guidelines/searching : "Aim to make your app's content searchable
  through a single location"; "Clearly display the current scope of a search" (placeholder text/token/title); suggestions and
  recents, with a way to clear history (privacy). Find-in-document is a separate, window-level pattern.

### 1.10 Colour, materials, typography
- Colour https://developer.apple.com/design/human-interface-guidelines/color [V]: "Avoid using the same color to mean different
  things" (status, interactivity); "Make sure all your app's colors work well in light, dark, and increased contrast contexts";
  use semantic colours "defined by its purpose, rather than its appearance"; "Avoid redefining the semantic meanings of dynamic
  system colors"; for colourful content "prefer a monochromatic appearance for toolbars". Near-bar rule: do not put similar colours in
  control labels and content behind them.
- Materials https://developer.apple.com/design/human-interface-guidelines/materials [V]: "Choose materials and effects based on
  semantic meaning and recommended usage"; thicker (more opaque) materials give better contrast for fine text; avoid the lowest
  vibrancy level on thin materials. (Liquid Glass transparency is not required for Adwaita; the lesson is legibility first.)
- Typography https://developer.apple.com/design/human-interface-guidelines/typography [V]: "Minimize the number of typefaces you use";
  built-in text styles "convey your information hierarchy through font size and weight" and carry weight+size+leading; font size
  "Follow the recommended default and minimum text sizes". "macOS doesn't support Dynamic Type" (so Mac apps must offer their own
  text-size setting; this applies to inkwell on Linux too). Large-size advice: keep information hierarchy, minimise truncation,
  "consider a stacked layout" when horizontally constrained.
- Accessibility https://developer.apple.com/design/human-interface-guidelines/accessibility [V]: "Strive to meet color contrast minimum
  standards" (WCAG and APCA named); provide higher contrast when Increase Contrast is on; "Be cautious with fast-moving and
  blinking animations" and honour Reduce Motion; "Prefer system-defined colors"; labels for VoiceOver.
- Motion https://developer.apple.com/design/human-interface-guidelines/motion [V]: "Add motion purposefully, supporting the experience
  without overshadowing it."; "Make motion optional"; "Aim for brevity and precision in feedback animations"; "generally avoid
  adding motion to UI interactions that occur frequently"; "Let people cancel motion ... don't make people wait for an animation to
  complete."

### 1.11 Menu-bar, windows: omitted (not needed; GNOME researcher covers header bar/menus).

### 1.12 Collaboration and sharing (the documented facts) [V]
https://developer.apple.com/design/human-interface-guidelines/collaboration-and-sharing
- "Place the Share button in a convenient location, like a toolbar, to make it easy for people to start sharing or collaborating."
- System share sheet / macOS sharing popover includes "ways to choose a file-sharing method and set permissions for a new collaboration".
- "Write succinct phrases that summarize the sharing permissions you support ... 'Only invited people can edit' or 'Everyone can make
  changes.'" The phrase sits in a button that reveals the options.
- "Provide a set of simple sharing options that streamline collaboration setup": who can access, edit vs read-only, whether
  collaborators can add people; "Keep the number of custom choices to a minimum and group them".
- "Prominently display the Collaboration button as soon as collaboration starts" - next to Share; it "reminds people that the content
  is shared and identifies who's sharing it."
- The collaboration popover has **three sections**: collaborators on top (with communication buttons), custom items in the middle,
  a manage button at the bottom ("Manage Shared File" by default). "Offer only the most essential items"; Notes "summarizes the most
  recent updates and provides buttons ... to get more information about the updates or view more activities."
- Notifications for "a change in the content or the collaboration membership, or the mention of a participant", each with a link
  that opens the relevant view.
- Pages help page (support.apple.com) [V]: "Everyone you invite can see changes as they're made, but you control who can edit or only
  view the document." Participant colours/cursors and the activity view are described on subpages that I could not read [U].
  https://support.apple.com/guide/pages/collaborate-on-a-document-tan6a2e3a0f6/mac
- Keynote/Freeform/Notes specifics beyond this (activity highlights, "@mentions") [U].
- Applied to inkwell: Share button (toolbar) -> popover with permission summary line + invite; Collaboration button with avatar stack ->
  popover (people, 1-3 recent changes, "Manage"). No separate panel for people.

### 1.13 Alternative reading: HIG as "restraint" rules
Distilled rules from sections above that map 1:1 to testable checks: <= 2 sidebar levels; one popover at a time; no alert for
undoable actions; every toolbar item deliberate, no default overflow; restore previous state on launch; shortcuts only for frequent
actions; every animation cancellable and optional.

### 1.14 Status, not alerts (inkwell-specific application)
Feedback page [V] + Alerts page [V]: show "saved/synced/peers" as an unobtrusive indicator in the window chrome; escalate to a
banner only when action is required (e.g. a file removed by its owner), to a modal only for irreversible loss.

## 2. What "Apple-level polish" concretely consists of (citable)

### 2.1 Progressive disclosure [V]
- Jakob Nielsen, "Progressive Disclosure", NN/g, 3 Dec 2006. https://www.nngroup.com/articles/progressive-disclosure/
- Rule: show "only a few of the most important options" first; advanced features on request; "it must be obvious how users progress";
  beyond **2 levels** designs "typically have low usability"; avoid multiple routes to the secondary level; decide the split from task
  analysis, frequency of use and usability tests (analytics alone can mislead).
- Use for: toolbar (formatting row), export options, share dialog advanced permissions, version history details, settings.

### 2.2 Content first, chrome reduction
- Apple Toolbars/Materials/Color [V]: background/tint minimisation, monochrome bars, content informs bars.
- Linear redesign write-up [V] https://linear.app/now/how-we-redesigned-the-linear-ui : "reduce visual noise", "alignment" of labels,
  icons and buttons that users "feel after a few minutes" rather than notice; chrome colours kept neutral; text and neutral icons
  darker in light mode and lighter in dark. Theme generated from three variables (base, accent, contrast) in **LCH** (perceptually
  uniform) instead of 98 per theme; contrast variable gives high-contrast themes for free.
- Things 3 (Cultured Code): "We believe simple is hard" and Apple's feature on the app stresses restraint / "unrivaled simplicity" [S]
  (search results quoting Apple's App Store story; page not read). https://apps.apple.com/us/story/id1390028519

### 2.3 Sensible defaults, direct manipulation, optional onboarding
- HIG Onboarding [V]: "Provide reasonable default settings"; postpone nonessential setup.
- HIG Drag and drop [V]: direct manipulation of files/blocks, with undo.
- Apple "Launching" [V]: restore state.
- NN/g heuristic 7 "Flexibility and efficiency of use" [V]: shortcuts "hidden from novice users" for experts.

### 2.4 Response-time thresholds
- Jakob Nielsen, "Response Times: The 3 Important Limits" (1993; 2014 update) [V] https://www.nngroup.com/articles/response-times-3-important-limits/
  - 0.1 s: "about the limit for having the user feel that the system is reacting instantaneously."
  - 1.0 s: "about the limit for the user's flow of thought to stay uninterrupted."
  - 10 s: "about the limit for keeping the user's attention focused on the dialogue."
- Doherty threshold [V, Laws of UX] https://lawsofux.com/doherty-threshold/ : productivity rises under **400 ms**; origin Doherty &
  Thadani, IBM Systems Journal, 1982. Takeaway: feedback within 400 ms; progress bars make waits "more bearable".
  Caveat: secondary summaries note 400 ms is a historical heuristic, not a universal limit [S].
- RAIL (Google) [V] https://web.dev/articles/rail : "Complete a transition initiated by user input within 100 ms" (process input events
  within 50 ms); each animation frame in <= 10 ms of work (16 ms budget at 60 fps, ~6 ms browser overhead); idle work in chunks
  <= 50 ms; "Beyond 1000 milliseconds, users lose focus." (page now says RAIL is a model for the web; numbers still the reference.)
- Application: keystroke -> glyph on screen < 100 ms (target one frame); preview refresh visibly staged (patch the changed page
  first); sidebar and popover open within one animation of 200-300 ms.

### 2.5 Animation duration and easing
- NN/g, Page Laubheimer, "Executing UX Animations: Duration and Motion Characteristics", 9 Feb 2020 [V]
  https://www.nngroup.com/articles/animation-duration/ : most animations **100-500 ms**; ~100 ms simple feedback (checkbox,
  toggle); 200-300 ms a modal; up to 400 ms big moves; popup appears ~300 ms, disappears ~200-250 ms (exit faster than enter);
  500 ms or more "feel like a drag"; ease-out for most (enter), ease-in/out acceptable for exits, avoid linear; frequent
  animations shorter and subtler; respect reduce motion. (Desktop/mobile split not in the article; use the general ranges.)
- Material Design 3 [S/U]: named durations from short1 = 50 ms up to extra-long4 = 1000 ms and an "emphasized" and "standard" easing;
  the official token page was not readable (JS). https://m3.material.io/styles/motion/easing-and-duration/tokens-specs
  Standard easing cubic-bezier(0.2, 0, 0, 1) seen only on an unofficial page [U]. Prefer NN/g numbers above.
- Apple Motion [V]: brevity, purposeful, optional, cancellable; no motion for frequent interactions.
- reduced motion: MDN [V] https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion :
  values `no-preference`/`reduce`; "Such animations can trigger discomfort for those with vestibular motion disorders"; swap
  large movement for a fade/colour change; Baseline widely available since Jan 2020. Under GNOME the equivalent system setting is
  "enable-animations"; the webview should map both.

### 2.6 Spacing grids, type scale, measure
- 4/8-pt grid: industry convention, no authoritative standards body source; Apple pages read give no grid [U]. Use it as a
  design-token rule (multiples of 4 px) and justify by concentric radii and rhythm (WWDC25 notes [V]).
- Measure: Bringhurst's 45-75 characters (66 ideal) for a single column - secondary sources only [S]
  https://webtypography.net/2.1.2 and https://www.viget.com/articles/the-line-length-misconception ; Butterick, Practical
  Typography [V]: "average line length of 45-90 characters" https://practicaltypography.com/line-length.html ; a 2005 study cited
  by Viget found reading speed highest at 95 characters [S]. WCAG 1.4.8 (AAA) [V]: "Width is no more than 80 characters or glyphs (40 if
  CJK)".
  https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html
  -> for a source editor, line wrapping at ~80 columns by default with a "reading width" cap; for the page preview, the page itself
  (print layout) fixes the measure - do not stretch preview text.
- Text spacing, WCAG 1.4.12 (AA) [V] https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html : content must not lose function
  when users set line height 1.5x, paragraph spacing 2x, letter spacing 0.12x, word spacing 0.16x font size. WCAG 1.4.8 (AAA)
  also wants line spacing >= 1.5 within paragraphs and no justified text [V].
- Type scale: Apple text styles [V] (size+weight+leading as a bundle); use a small fixed scale and at most 2 typefaces
  ("Minimize the number of typefaces").
- Optical alignment: Linear alignment write-up [V] (labels/icons aligned until the eye stops noticing). Quantitative guideline: [U].

### 2.7 Skeletons, spinners, progress, optimistic UI
- NN/g "Skeleton Screens 101" (Samhita Tankala, 4 Jun 2023) [V] https://www.nngroup.com/articles/skeleton-screens/ : under 1 s use none;
  spinner for 2-10 s single module; skeleton for full-page loads < 10 s; progress bar > 10 s with estimate;
  file conversions/uploads use a progress bar, not a skeleton; frame-only skeletons (header + footer) must not stand in for progress.
- NN/g "Progress Indicators Make a Slow System Less Insufferable" (Katie Sherwin, 26 Oct 2014) [V]
  https://www.nngroup.com/articles/progress-indicators/ : no indicator < ~1 s; looped spinner 2-10 s with text ("Loading comments");
  percent-done >= 10 s or counted work ("Updating address 3 of 50"); avoid static indicators and "don't click again" warnings -
  "show that the first click was accepted instead".
- Apple Loading [V]: show placeholders immediately, allow other work meanwhile.
- Optimistic UI: only secondary sources [S] (show expected result, roll back on failure; recommended when success rate is very high,
  not for payments/destructive ops). For a local-first editor the "optimistic" state is the *real* state (Ink & Switch ideal 1,
  section 5.1), so there is nothing to roll back for text edits; use it for invitations/exports only.
- Typst compile (preview): treat as a 2-10 s "module" load only for cold start; incremental recompiles should be invisible
  (keep last good page on screen, show an error badge, never blank the preview). [design inference from NN/g + HIG Loading]

### 2.8 Empty states
- NN/g, Kate Kaplan, "Designing Empty States in Complex Applications: 3 Guidelines", 19 Sep 2021 [V]
  https://www.nngroup.com/articles/empty-state-interface-design/ : communicate system status ("Do not default to totally empty
  states"; do not show "No records" before data has loaded); use empty states as learning cues ("pull revelations", e.g. "Star your
  favorites to list them here."); give a direct pathway (button, link, demo data).
- Apple Onboarding [V]: contextual tips beat a big flow.

## 3. UX science and standards with exact references

### 3.1 Nielsen's 10 heuristics [V] (NN/g, updated 30 Jan 2024) https://www.nngroup.com/articles/ten-usability-heuristics/
1 Visibility of system status - "The design should always keep users informed about what is going on."
2 Match between system and real world - "The design should speak the users' language."
3 User control and freedom - "They need a clearly marked 'emergency exit'."
4 Consistency and standards - "Users should not have to wonder whether different words, situations, or actions mean the same thing."
5 Error prevention - "the best designs carefully prevent problems from occurring in the first place."
6 Recognition rather than recall - "Minimize the user's memory load by making elements, actions, and options visible."
7 Flexibility and efficiency of use - "Shortcuts - hidden from novice users - may speed up the interaction for the expert user."
8 Aesthetic and minimalist design - "Interfaces should not contain information that is irrelevant or rarely needed."
9 Help users recognize, diagnose, recover from errors - "Error messages should be expressed in plain language (no error codes)."
10 Help and documentation - "It's best if the system doesn't need any additional explanation."

### 3.2 Laws of UX [V list from https://lawsofux.com/]
- Fitts's Law: "The time to acquire a target is a function of the distance to and size of the target." -> big hit areas, edge/corner
  targets (header bar buttons), related controls close.
- Hick's Law: "The time it takes to make a decision increases with the number and complexity of choices." -> menus short, grouped.
- Miller's Law: "7 (plus or minus 2) items in their working memory" as stated by Laws of UX (note: the original is about span of
  immediate memory; the site is a popular summary). -> chunk lists (people, versions).
- Jakob's Law: users expect your product to work like the others they know -> follow GNOME/Apple conventions (Ctrl+S, Ctrl+F, Ctrl+Z).
- Tesler's Law (conservation of complexity): "for any system there is a certain amount of complexity which cannot be reduced" ->
  absorb P2P complexity in the system, not the user.
- Aesthetic-Usability Effect: "Users often perceive aesthetically pleasing design as design that's more usable." NN/g
  (https://www.nngroup.com/articles/aesthetic-usability-effect/ [V], published 3 Feb 2024): first studied by Kurosu & Kashimura
  (Hitachi, 1995, 26 ATM interface variations, 252 participants). Consequence: polish buys tolerance for minor faults, but NN/g
  warns attractive != more usable; do not use it to excuse real defects.
- Peak-End Rule: judged mainly "by how it felt at its peak and at its end" -> make the end of tasks (export done, invitation
  accepted) a clear, pleasant moment.
- Zeigarnik Effect: "People remember uncompleted or interrupted tasks better than completed tasks" -> show unfinished state
  (pending invitations, unsent exports) discreetly; resume interrupted flows.
- Postel's Law: "Be liberal in what you accept, and conservative in what you send." (also protocol rule) -> paste/drop anything,
  normalise.
- Doherty Threshold 400 ms (section 2.4). Law of proximity / common region / similarity (grouping) [V list].
- Flow, Cognitive load, Paradox of the active user ("Users never read manuals but start using the software immediately") [V list].

## 5. Local-first / peer-to-peer UX research

### 5.1 Ink & Switch, "Local-first software" (Kleppmann et al., 2019) [V]
https://www.inkandswitch.com/essay/local-first/
Seven ideals with quotes: "No spinners: your work at your fingertips" ("there is never a need for the user to wait for a request to
a server to complete"); "Your work is not trapped on one device"; "The network is optional" ("the user can read and write this data
anytime, even while offline"); "Seamless collaboration with your colleagues"; "The Long Now"; "Security and privacy by default";
"You retain ultimate ownership and control".
UI findings from the essay:
- Sync state: many apps show server sync status; local-first apps need to say "online and offline states" when each device holds a
  different copy; P2P systems "are never fully 'online' or 'offline'", so a binary indicator may not fit.
- Offline: Google Docs "blocks editing of the document" when offline (the essay's counterexample); local-first prototypes keep
  working, removing the anxiety about whether work will be there.
- Conflicts: Dropbox "conflicted copy" and Evernote's separate notebook are poor; Pixelpusher highlights conflicting pixels in red;
  Automerge keeps conflicting values for the app/user to resolve - conflicts arise only on the same property of the same object.
- History: time-travel view with highlighted changes (Trellis); git-inspired branch/merge (Pixelpusher).
- Sharing: URL sharing works well; but with a local copy "stop sharing" is hard to define (what does revoking mean?). This is
  precisely inkwell's share/revoke semantics: say plainly what revocation can and cannot do.
- Presence: avatars in toolbar, ephemeral selection highlights (PushPin).
- Design implications (inference): text merges never need a "conflict" UI; show "N changes from <person> merged" instead; reserve
  explicit conflict UI for non-mergeable properties (file rename vs delete, same-name file creation).

### 5.2 Showing sync status without anxiety (synthesis; the essay and HIG are the evidence)
- HIG Feedback [V]: status passive and nearby; escalate by importance. HIG Alerts [V]: not for information-only events.
- NN/g heuristic 1 [V]: keep users informed; Progress rules [V]: no spinner under ~1 s, text with spinner, explicit counts.
- Doherty/RAIL [V]: acknowledge input within 100-400 ms; for local-first the acknowledgement is the local edit itself.
- Proposed vocabulary (inference, not a citation): "Saved on this computer" (always true), "Shared with 3 people", "Waiting to
  reach Anna", "Up to date as of 14:02"; never "Offline" as an error; avoid red except for action-required (e.g. disk full).
- No empirical study on sync-indicator anxiety was found in this research [U]; search for one returned only generic loading
  psychology blogs. Treat anxiety reduction as design hypothesis to test with the project's ux-walkthrough.

### 5.3 Trust, invitations, verification
- Bicakci et al., "How Safe Is Safety Number? A User Study on SIGNAL's Fingerprint and Safety Number Methods for Public Key
  Verification", ISC 2018, LNCS 11060 pp. 85-98, DOI 10.1007/978-3-319-99136-8_5 [S - abstract only]: 42 participants; the safety
  number method led to more successful verifications in less time than the older fingerprint.
  https://unpaywall.org/10.1007%2F978-3-319-99136-8_5
- Turner, Shahandashti, Petrie, "The Effect of Length on Key Fingerprint Verification Security and Usability", ARES 2023 [V]
  https://ar5iv.labs.arxiv.org/html/2306.04574 : 162 valid participants (186 recruited), numeric fingerprints of 1/2/3 lines
  (20/40/60 digits), 20 comparisons each. Mean comparison time 6.1 / 7.4 / 10.0 s. False acceptance (missed attack on a nearly
  identical pair) 13.2 % / 30.9 % / 43.5 %; false rejection 0.9 / 2.7 / 2.0 % (n.s.). Authors: manual verification of long
  fingerprints has poor usability; the 60-digit fingerprint gives ~96-bit practical, not 112-bit, security. They recommend
  complementary or alternative methods for high-security contexts.
  -> design implication (inference): do not ask people to eyeball a long fingerprint; use one-time out-of-band codes/QR, show
  the short code once, and make mismatch detection easy (read aloud, 3 groups).
- Matrix/Element: spec has SAS verification with `decimal` and `emoji` methods [V as table of contents only]
  https://spec.matrix.org/latest/client-server-api/#sas-verification ; Matrix docs say clients supporting emoji SAS "should at least
  offer numerical verification" for devices that cannot show emoji [S]. No usability study of emoji verification was found [U];
  the commonly cited facts "7 emoji from 64" are from memory [U].
- Zed [V] shared-project warning: sharing a project "gives collaborators access to your local files", so "collaborate only with
  people you trust". Plain trust statement near the invite action.
- Apple HIG Collaboration [V]: permission summary phrase and "Manage" place; notifications for membership changes ("join, or leave").
  -> notify when someone joins/leaves, not only when they edit.

### 5.4 Offline indicators, empty states, first run
- Offline: do not block editing (Ink & Switch [V]); NN/g empty-state guidance [V] "Do not default to totally empty states";
  HIG Onboarding [V] fast, optional, contextual; HIG Launching [V] restore state.
- First run (inference from the above): open straight into a sample or the last document; an empty files sidebar shows one
  sentence and two buttons ("New document", "Open a folder") and a demo "Try the preview" link (NN/g "direct pathways").

### 5.5 Export flows
- No authoritative export-flow guideline fetched [U]. Applicable verified rules: HIG Sheets [V] (one sheet, Cancel + primary
  button, self-contained task may deserve its own window), NN/g progress rules [V] (counts and percent for >= 10 s; "Exporting page
  3 of 12"), HIG Alerts [V] (confirm completion only when important; otherwise inline status with "Show in folder").

## 6. Quick checklist derived only from [V] sources (each line has its anchor above)
- One Share button in toolbar; permission phrase; Collaboration popover (people / essentials / manage). 1.12
- Toolbar items deliberate; no default overflow; neutral, monochrome chrome; focus mode restorable. 1.3, 2.2
- Sidebar <= 2 levels, hideable, not hidden by default. 1.4
- Popover: one at a time, saves on dismiss, no warnings in popovers. 1.5
- No alert for undoable/common actions; alert titles specific, <= 2 lines, max three buttons. 1.6
- Restore last state on launch; launch instantly; show placeholders at once. 1.7
- Undo is multi-level, labelled, and scrolls/highlights the restored result. 1.8
- Shortcuts only for frequent commands; never override standard ones; palette lists all commands. 1.9, 4.1
- Contrast: 3:1 for UI and states, 4.5:1 text [U for 4.5]; higher-contrast and reduced-motion modes. 3.5, 3.7
- Targets >= 24 CSS px; focus never entirely hidden. 3.5
- Animations 100-500 ms, ease-out, cancellable, optional. 2.5
- Input response < 100 ms; spinner only after ~1 s; progress with counts after 10 s. 2.4, 2.7
- Text spacing survives user override (1.5 / 2 / 0.12 / 0.16). 3.5
- Presence = colour + name; follow by click, stops on input. 4.5
- Named versions + author-coloured diff + non-destructive restore. 4.6
- Short verification codes, not long fingerprints. 5.3
