## A. Showing differences between versions of prose
---------------------------------------------------------------------

### A1. Granularity: character vs word vs line (READ)
- Pattern: diff prose by words (or sentences), never raw characters. Run a "semantic cleanup" pass that absorbs tiny coincidental matches, and align edit boundaries on word or punctuation boundaries.
- Why: character diffs find accidental common letters (the alphabet is small), so a rewritten word shows as confetti. Word diffs give fewer, larger, readable edits.
- Quotes (Neil Fraser, diff strategies): "This problem is most apparent in character-based differences since the small set of alphanumeric characters ensures commonalities." And: "Copy/insert differences are generally not human-readable."
- Same page: semantic cleanup "has tunnel vision; it is unable to see beyond the immediate neighbourhood of each equality". Semantic alignment shifts edit boundaries to whitespace/punctuation/line breaks.
- diff-match-patch README (SEARCH-ONLY): `diff_cleanupSemantic` is "for human-readable" diffs; example turns a fragmented diff into one `mouse -> sofas` replacement. `diff_cleanupEfficiency` is for machines.
- URL: https://neil.fraser.name/writing/diff/
- inkwell implication: Automerge keeps every keystroke, but the UI diff must be computed on words/sentences between two chosen points, then cleaned, not replayed per keystroke.

### A2. Myers vs patience vs histogram (SEARCH-ONLY, secondary sources)
- Pattern: Myers (git default) = shortest edit script; patience (Bram Cohen) anchors on unique lines then recurses; histogram (JGit) extends patience by picking low-occurrence common elements.
- Why: Myers can produce confusing alignments when blocks move; patience/histogram anchor on unique units.
- Caveat: these are line-oriented code diffs. For prose, the unit would be words/sentences; the benefit of "anchor on rare tokens" may carry over but I found no prose-specific evidence. UNVERIFIED for prose.
- URLs: https://blog.jcoglan.com/2017/09/19/the-patience-diff-algorithm ; https://lore.kernel.org/git/20180810001010.58870-2-sbeller@google.com/T/ (both SEARCH-ONLY).

### A3. Ink & Switch Upwelling: diff of prose, drafts, review (READ)
- URL: https://www.inkandswitch.com/upwelling/
- Findings relevant to inkwell:
  - Prose diff: Upwelling "avoid[s] rendering deleted text in a strikethrough font". Insertions get a light background; deletions are a small marker, with hover revealing the removed text. (Paraphrase from fetch; the exact glyph was reported as an emoji.)
  - Change grouping: Google Docs and Word "treat every consecutive sequence of character insertions or deletions as a separate suggestion", cluttering the margin. A draft's title states its purpose so related edits are grouped.
  - One interviewee said reading Track Changes is "nearly impossible" with heavy edits.
  - Always record edits and let readers toggle the view, instead of needing "turn on tracking" before editing.
  - Drafts are "layers"; any collaborator may merge any draft (social convention, no permissions). Unmerged = "drafts", merged = the "stack" holding full history.
  - Concurrent merge pitfalls: "white" changed to "frosty" in one draft and "soft" in another can produce "frostysoft" or "softfrosty", so human review is required. Deleting a paragraph in one draft while editing it in another keeps the inserted characters.
  - Writer privacy ("fishbowl effect"): "Writers don't want first drafts visible to the editor." Writers worked around it by copying to private files or going offline. This argues for private drafts in a peer-to-peer app.
  - Dependent drafts (a draft on a draft) "added complexity without much value"; long-lived branches raised conflict risk. Keep drafts small, merge quickly.
  - Not built: inline accept/reject per change (designed only); prototype accepts/rejects per draft.

### A6. Inline vs side-by-side: the evidence is weak (SEARCH-ONLY)
- Eye-tracking study on code review, 12 participants: no significant difference between split and unified views for bug detection (SEARCH-ONLY, repositorio.uc.cl link in results).
- An older SFU paper on single-pane text version comparison reports "60% faster" comparison tasks for single-pane vs two-pane in a 16-participant usability study (search snippet only; I downloaded the PDF but could not read it; UNVERIFIED). URL: https://vvise.iat.sfu.ca/user/data/papers/version4text.pdf
- Perforce Swarm doc (SEARCH-ONLY): users find unified view easier to locate changes, then switch to side-by-side to understand them.
- Honest conclusion: no controlled prose study found. Choose by task: inline for reading flow and review; side-by-side only for comparing two whole versions. Offer one default (inline) and a toggle.
- Eye-tracking on edited prose (Carrol et al. 2015, SEARCH-ONLY): lexical changes lengthened reading of the rest of the sentence; punctuation changes only the changed portion. Not about markup. https://benjamins.com/catalog/ssol.5.2.05con

### A11. Accessibility of diff colours
- WCAG 1.4.1 (READ): https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html
  - "Color is not the only way of distinguishing information."
  - A red/green pair can pass if the two also differ in lightness by at least 3:1 contrast; technique G14: make information conveyed by colour available in text too. The page does not mention diffs; applying it to diffs is my inference.
  - Rule for inkwell: insertion = colour + underline (or soft background + marker); deletion = colour + strike-through or a glyph; never colour alone.
- GitHub colour-blind themes (SEARCH-ONLY): replaces red/green diff colours with orange/blue; split into protanopia/deuteranopia and tritanopia themes; community thread reports blue/orange scheme is inaccessible for tritanopia. https://github.blog/changelog/2022-04-19-protanopia-deuteranopia-colorblind-themes-beta/ (READ: only high-level text, no colours listed); https://github.com/community/community/discussions/6385 (SEARCH-ONLY).
- Pattern: ship a diff palette that varies in lightness (not hue only) plus a non-colour cue; make it follow the system high-contrast setting.

### A12. Author colours in diffs and text

- iA Writer Authorship (READ): https://ia.net/writer/support/editor/authorship : human text in "subtle tones", AI text in a gradient, reference text dimmed; "Writer relies on you defining the authorship by yourself"; metadata stored at end of file, stripped on export; "Everything happens locally". Pattern: authorship is a toggled overlay, off by default, stripped from exports.
- Google Docs "Show editors" (SEARCH-ONLY): select text, right-click: panel lists each editor with their latest edit and time, link to version history. https://workspaceupdates.googleblog.com/2021/05/view-more-context-on-google-docs-edits-with-show-editors.html

## B. Version history for writers
---------------------------------------------------------------------

### B1. Google Docs (READ)
- URL: https://support.google.com/docs/answer/190843
- Grouped versions in the right panel ("Expand" to see them), "Name this version", toggle "Only show named versions", "Restore this version", "Last edit" at the top. Limit stated: up to 40 named versions per document.
- The page does NOT mention per-author colours in history; "Show editors" is a separate feature (see A12). Claim "history highlights changes per author colour" is UNVERIFIED from this page.
- Pattern: automatic sessions + optional names + filter to named only.

### B2. Notion (READ)
- URL: https://www.notion.com/help/duplicate-delete-and-restore-content
- "A new version of a particular page will be recorded every 10 minutes as you actively edit it", plus one two minutes after last edit. Retention: 7 days free, 30 Plus, 90 Business, unlimited Enterprise. Restore is reversible ("You can return to any earlier version afterward"); partial recovery by copying blocks from an old version. Honest limit: "Version history shows the main highlights, but it won't capture every single change."
- Trash 30 days, then another 30 days kept; deleted page cannot be edited unless restored.

### B3. Figma (READ)
- URL: https://help.figma.com/hc/en-us/articles/360038006754-View-a-file-s-version-history
- Autosave checkpoint "every 30 minutes" plus on connection drop/crash; named versions with title (clipped at 25 chars) and description (under 140 chars shown in full); autosaves are grouped, expand to see each; "Show older" to load more; each version shows main contributor's name and avatar.
- Restore: "This is a non-destructive action." Figma adds two checkpoints (current state and restored version). Duplicate creates a new file from that version.

### B4. Overleaf (READ)
- URLs: https://docs.overleaf.com/writing-and-editing/history-and-versioning (READ). Also https://www.overleaf.com/blog/154-a-first-look-at-the-new-version-comparison-feature (SEARCH-ONLY).
- Labels: "Version labels allow you to identify key milestones in a project"; multiple labels per version; current is "Current state". Compare by picking a range with "Align Start / Align End"; restore a single file or the whole project; restore keeps "comments and tracked changes". Free plan: last 24 hours plus labelled versions (limits of the free tier, not a design goal).
- Page does not describe grouping or per-author colours (UNVERIFIED there); older posts (SEARCH-ONLY) say additions green, deletions red strikethrough.

### B5. Apple Pages (READ)
- URL: https://support.apple.com/guide/pages/tan7f1de6ec5/mac
- "Browse All Versions": current version on the left, earlier versions as a stack on the right with a timeline; click tick marks or arrows; "Restore" replaces current; Option-click gives "Restore a Copy"; you can select text from an old version and copy it into the current one.
- Shared docs: editors "can copy and restore only the versions created after you shared the document"; view-only users cannot access earlier versions. Useful precedent for "which history is shared".
- No naming of versions on that page.

### B6. Etherpad timeslider (SEARCH-ONLY)
- Scrub through full history character by character, author colours. https://github.com/ether/etherpad
- Third-party account of old design: snapshot at every tick was costly (https://features.jsomers.net/how-i-reverse-engineered-google-docs/, SEARCH-ONLY).

### B7. Patterns for writers (from the above)
1. Automatic sessions grouped by time gap and author (Patchwork "author and edit time", READ; Notion 10 min/2 min, READ; Figma 30 min, READ). Exact gap that works best: no published study (UNVERIFIED).
2. Named versions are optional and filterable (Google, Figma, Overleaf labels, all READ).
3. Timeline scrubber (Pages, READ; Etherpad, SEARCH-ONLY).
4. Preview before restore and restore never destructive (Figma READ, Notion READ, Pages "Restore a Copy" READ).
5. Copy a piece from an old version (Pages READ, Notion READ).
6. "What changed since I last looked": Word's reviewing pane count (READ); a per-user "last seen" marker is my inference, no source found (UNVERIFIED).
7. Attribution: iA Writer (READ), Google "Show editors" (SEARCH-ONLY), Etherpad colours (SEARCH-ONLY).
8. Parallel drafts without git words: Upwelling "drafts" (READ), Patchwork "branch" (READ, they kept the word), Figma "branch/main file/Review and merge/Get updates from main" (READ, Figma keeps the git words; names for UI: Active/Archived/Yours tabs), Google Docs suggestions (SEARCH-ONLY).
9. Merge a draft back with review: Figma "Approve changes / Approve and merge branch / Suggest further changes" (READ), Upwelling any collaborator may merge (READ).

### B8. Git GUIs' graphs (what NOT to show) (UNVERIFIED)
- I did not fetch GitKraken, Fork, Sublime Merge or gitk docs. Ink & Switch's own note (READ, A4/entry 09) says they wanted "a way to show the relationship between branches" without a complex diagram, which supports not showing a lane graph to writers. If a graph is unavoidable: keep it to at most two lanes (main + the current draft), as Patchwork restricts branches to start and end at main (READ, entry 06).

### B9. Local-first, peer-to-peer: shared vs personal history
- Upwelling (READ): privacy of first drafts matters ("fishbowl effect"); drafts can be private, merged work joins the shared stack.
- Pages (READ): shared-document editors only see versions since sharing; useful as a rule for newcomers.
- Patchwork (READ): same Automerge history can be grouped by author or time; their timeline swaps entirely on branch switch (open problem).
- No source found on how concurrent offline edits appear in a history list (gap). Suggested presentation derived from Patchwork's grouping: one entry per person and session, merged offline sessions shown at the time they were reconnected, with an "edited offline" label (my inference, UNVERIFIED).
- Automerge history API docs: my fetch returned 404 (https://automerge.org/docs/reference/documents/history/); UNVERIFIED.

### C10. Conflicts and deletion in shared projects
- Dropbox (READ): https://help.dropbox.com/organize/conflicted-copy : conflicted copy name = file name + editor's username + "conflicted copy" + date; "The last version saved will always appear as the conflicted copy." Caused by simultaneous edits, offline edits, or an open file auto-saving on another computer.
- Syncthing (READ): https://docs.syncthing.net/users/syncing.html : `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`; older modification time becomes the conflict copy; a modify-vs-delete conflict can also produce a conflict copy; conflict copies propagate to all devices as normal files.
- Lesson: file-copy conflict naming is jargon-heavy and pollutes the tree. inkwell's text is a CRDT, so only whole-file operations (rename, move, delete vs edit) can conflict. Suggested wording and behaviour is my design inference, not sourced: a deleted file that someone else edited reappears with a short banner "Ana edited this while Marc deleted it" and offers Keep / Remove.

## D. Tabs for documents
---------------------------------------------------------------------

### D1. GNOME HIG tabs (READ)
- URL: https://developer.gnome.org/hig/patterns/nav/tabs.html
- Tabs let "a window to contain a mutable set of content items, such as pages, documents or images", mainly for editor and browser apps.
- Bar visibility: if tabs are central keep the bar visible; otherwise hide it until a second tab opens (this is autohide).
- Naming: icon and label only "if it is necessary"; short labels, most useful part first so it survives truncation.
- Context menu: end with "Close"; "Move to New Window" if supported; avoid "left/right" wording (RTL).
- Shortcuts to support: Ctrl+T, Ctrl+W, Ctrl+Page Up/Down, Ctrl+Home/End, Ctrl+Tab, Alt+1..9.
- Pin/Unpin is an optional context menu item. The page gives no maximum number of tabs and no overview guidance.

### D2. libadwaita AdwTabView / AdwTabBar / AdwTabOverview (READ)

### D4. Evidence for and against tabs for writers

- Obsidian forum (SEARCH-ONLY): some users want tabs removed and prefer keyboard navigation; another keeps tabs because a tab remembers the cursor position. Anecdotal. https://forum.obsidian.md/t/disabling-tabs-or-what-use-are-they/46669

- Alternative (single document + quick switcher + recents): Obsidian quick switcher READ (C5); Ctrl+P in VS Code READ (C2). Evidence is design practice, not measured.
- Practical reading: a writing project usually has few open files at once; use tabs with autohide (hidden until a second file is open, HIG READ), preview-style reuse, plus a switcher.

## F. Showing other people's changes inside the text area
---------------------------------------------------------------------
Evidence is thin: no controlled study of remote carets during prose writing was found. Most items below are mechanisms from docs plus design inference (marked).

### F1. Research on awareness
- Dourish and Bellotti 1992 (SEARCH-ONLY, abstract): awareness is usually supported by active mechanisms; the paper argues for information "provided and used passively through the shared workspace"; its case study ShrEdit gave "shared feedback" of editing activity. PDF text was garbled, so exact wording is UNVERIFIED. https://www.dourish.com/publications/1992/cscw92-awareness.pdf
- Gutwin and Greenberg 2002 (SEARCH-ONLY): workspace awareness is the "up-to-the-moment understanding of another person's interaction with a shared workspace"; framework = elements of knowledge, perceptual mechanisms, uses in collaboration. The who/what/where/when question list is not confirmed by the pages seen (UNVERIFIED). https://collablab.northwestern.edu/CollabolabDistro/nucmc/GutwinGreenberg_FrameworkWorkspaceAwareness.pdf
- Telepointers and multi-user scrollbars help awareness but "are not sufficient alone" (ADCS 2004 paper, SEARCH-ONLY, https://people.eng.unimelb.edu.au/ammoffat/adcs2004/papers/paper05.pdf). Telepointer traces help interpret gestures under lag (Gutwin and Penner, SEARCH-ONLY).
- Distraction: one 2026 arXiv study of an AI agent's moving cursor found participants reporting distraction ("broke their train of thought") but also better predictability (SEARCH-ONLY, https://arxiv.org/pdf/2605.24729). Figma, Miro and Lucid users ask for a way to hide cursors (forum posts, anecdotal, SEARCH-ONLY, e.g. https://forum.figma.com/t/make-show-multiplayer-cursors-setting-sticky-across-sessions/20614). No controlled study with and without cursors for writing found (gap).

### F2. Remote carets and selections
- Yjs awareness (READ): https://docs.yjs.dev/getting-started/adding-awareness : cursor location is shared through a "cursor" field; identity through a "user" field used "to render the cursor object in a unique color"; presence is kept out of the document: "Awareness information isn't stored in the Yjs document, as it doesn't need to be persisted across sessions"; when you go offline "your own awareness state is automatically deleted". No timeout value given. Convention for Automerge: presence is likewise ephemeral, sent beside the document (Automerge-repo presence not fetched, UNVERIFIED).
- Figma (SEARCH-ONLY): cursor chat is a temporary bubble that fades after inactivity (FigJam help, https://help.figma.com/hc/en-us/articles/4403130802199). A design guide describes name label shown while active and a 50 percent faded cursor when away; not from Figma, UNVERIFIED.
- Google Docs, Zed, VS Code Live Share, CodeMirror collab cursors (name flag timing, duration): not found (UNVERIFIED). The CodeMirror decoration example page does not mention collaboration cursors (READ, negative).
- Design inference (unsourced): coloured caret with a small name flag that appears when the person types or moves and hides after a few seconds idle; selection as a tinted band with the same colour; each person's colour also carries a non-colour cue (initial in the flag).

### F3. Marking text someone just wrote
- Upwelling (READ, A3): insertions get a light background, deletions a small marker with hover to reveal; contributions highlighted by author in a draft.
- Patchwork (READ, A4): inline diff in the editor with additions highlighted; minibar of where changes lie; hover to show deleted text.
- iA Writer authorship (READ, A12): different tone per source; toggled on demand.
- Word Simple Markup (READ, A5): "displays tracked changes with a red line in the margin" (change bar in the margin, text left clean).
- Google Docs "See new changes", Notion, Slack unread line: not fetched (UNVERIFIED).
- Pattern (inference): a brief tint on newly arrived text that fades over a few seconds, a margin tick for "changed since you last looked", cleared when you scroll past or press a button.

### F4. Persistent authorship on demand
- iA Writer (READ): toggle with a shortcut, human text in subtle tones, metadata stripped on export.
- Google Docs "Show editors" (SEARCH-ONLY): select text, panel lists each editor with latest edit and time. https://workspaceupdates.googleblog.com/2021/05/view-more-context-on-google-docs-edits-with-show-editors.html
- Etherpad authorship colours with a toggle (SEARCH-ONLY, https://github.com/ether/etherpad).
- Hover card with name and time: pattern implied by Google, inference otherwise.

### F5. Edits arriving off-screen, scroll stability
- MDN overflow-anchor (READ): https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor : scroll anchoring "adjusts scroll position to minimize content shifts" and "is enabled by default in any browser that supports it"; it can be turned off per element with `overflow-anchor: none`. The page does not itself explain the above-the-viewport case (my paraphrase of the spec behaviour is marked as not on that page). Relevance: in a webview the browser already keeps the visible text still when content grows above, unless the editor virtualises lines and breaks anchoring (UNVERIFIED for CodeMirror 6; test it).
- Off-screen chips ("Bob is editing line 120"): no source found (UNVERIFIED). Related READ: VS Code overview ruler shows problem marks (E3) and Patchwork minibar (A4) are the precedents for an edge strip with per-author ticks.
- Multi-user scrollbars are named as an awareness aid (SEARCH-ONLY, ADCS 2004 paper).

### F6. Deletions by others, concurrent edits in my sentence
- Google Docs screen-reader mode (SEARCH-ONLY): "Deleted text is crossed out" and read as "deleted". https://support.google.com/docs/answer/6239410
- Upwelling (READ): deleted text as a marker with hover, not strikethrough; CRDT merge of two edits to the same word can give "frostysoft" so a human must review (A3). Concurrent edits inside my own sentence therefore need a visible mark of who changed what, with the option to see the result of the merge.
- Ghost strike-through that fades, margin tick: inference, no source.

### F7. Collaborative undo
- Yjs UndoManager (SEARCH-ONLY): selective undo scoped by `trackedOrigins`; practice is to track the local client only (Tiptap example). A forum thread questions whether the stack is truly per-user (https://discuss.yjs.dev/t/how-to-use-undomanager-in-best-practice/1340). https://docs.yjs.dev/api/undo-manager
- Zed (READ): "Undo and redo are not available when collaborating in a project shared by someone else" (file operations, C4). Shows that file-level undo is hard in shared projects.
- Expectation (inference): Ctrl+Z undoes only my own last change, even if others typed after; say so in a toast when the undone text was already edited by someone else.

### F8. Density limits and reduced motion
- No source on how many simultaneous carets are tolerable (UNVERIFIED). Design inference: past about 4 people show carets without flags and a count chip, show flags on hover; respect the system reduced-motion setting by replacing fade animations with an instant tint and a static margin mark.
- Cursor-hiding requests across Figma, Miro and Lucid (SEARCH-ONLY, F1) support a global "hide others' cursors" switch that is remembered across sessions.

### F9. Accessibility
- WCAG 1.4.1 (READ, A11): colour alone insufficient; every author needs a non-colour cue (initial, underline style, flag text).
- WCAG 1.4.11 Non-text Contrast (READ): https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html : "3:1" against adjacent colours for UI parts needed to identify components and states; "A computed ratio of 2.999:1 does not pass." A caret and flag need 3:1 against the page background; a tinted highlight of text is text background and falls under text contrast 1.4.3 (my reading; not stated on the page).
- Google Docs screen-reader support (SEARCH-ONLY): "Show live edits" sidebar lists each entry with name, avatar, timestamp and change type ("add", "replace"); follow one collaborator or all; shortcut Ctrl+Alt+Shift+R; screen reader can announce people entering and leaving, switchable off; many suggestions make announcements hard to follow. https://workspaceupdates.googleblog.com/2019/08/real-time-collab-accessibility.html ; https://support.google.com/docs/answer/6239410
- Pattern: remote changes go to a polite live region or a sidebar log, never interrupt typing; announcements are opt-in per person.

## Strongest, best-evidenced patterns
---------------------------------------------------------------------

### Surface A (differences)
1. Diff by words (and sentences), then apply semantic cleanup; never raw character diffs (Fraser, READ).
2. Single-column inline default; side-by-side only as an optional toggle; the evidence for either is weak, so decide by task (A6, SEARCH-ONLY).
3. Avoid heavy strikethrough: hover or marker for deletions, or "before -> after" in the margin for replacements (Upwelling, Patchwork, both READ).
4. Never colour alone: add underline for insertions and strike/glyph for deletions, and keep lightness contrast of at least 3:1 (WCAG 1.4.1, READ).
5. A quiet-to-full markup switch (marker only / full / final / original) modelled on Word's four views (READ).
6. Collapse unchanged stretches into expandable bars (VS Code, READ) and show a minibar of where changes lie (Patchwork, READ).
7. Next/previous change with a count, accept/reject moves on to the next change (Word, READ).
8. A short summary of the change first, in words/sentences, optionally AI-written (Patchwork, READ).
9. Moved paragraph = one marked move, not delete+insert (MediaWiki arrow, READ; VS Code moves, SEARCH-ONLY).
10. Rendered view beside source view (GitHub, SEARCH-ONLY) and a page overlay for layout changes (Figma READ, diff-pdf SEARCH-ONLY).

### Surface B (history)
1. Automatic sessions, grouped by author and time gap, with optional names and a "named only" filter (Google, Figma, Overleaf, Patchwork, all READ).
2. Restore is never destructive: it creates a new version, and "restore a copy" and copy-a-passage are available (Figma, Notion, Pages, all READ).
3. Timeline view with preview before restore (Pages, READ).
4. Show a merged draft as one history item, so finishing a batch of work feels like one thing (Patchwork, READ).
5. Always record, toggle the view; do not make people turn tracking on (Upwelling, READ).
6. Drafts: small, short-lived, one level, from the main text and back to it (Upwelling, Patchwork, READ). Keep git words out; "draft" is the better word (Upwelling).
7. Authorship as an overlay you toggle, off by default (iA Writer READ, Google "Show editors" SEARCH-ONLY).
8. Private drafts matter to writers (Upwelling "fishbowl effect", READ).
9. History visible to a newcomer starts when they joined (Pages, READ) is one defensible rule; decide explicitly.
10. Gaps: no source on offline-merge presentation or on the best session gap.

### Surface C (file browser)
1. Keyboard model: ARIA tree keys, type-ahead, Home/End, `*`, multi-select (APG, READ).
2. A fuzzy "find or create" switcher in front of the tree for big projects (Obsidian, VS Code Ctrl+P, READ).
3. Tree filter with highlight/filter toggle and fuzzy match (VS Code, READ); "show the open file in the tree" (JetBrains, READ).
4. Fold single-child folders into one row (Zed READ, JetBrains SEARCH-ONLY).
5. Status propagates up: a problem or a change inside a folder shows on the folder (Zed diagnostics, READ).
6. Deleting: undo toast, not a confirmation (GNOME HIG, toasts READ, destructive-actions SEARCH-ONLY); recoverable trash with a retention time (Notion, READ).
7. Shared-project caution: Zed's guests cannot trash, only delete permanently (READ), so recoverable delete must be designed in.
8. The "main document" = the file previewed and exported (Typst app, READ).
9. Conflict wording: avoid "conflicted copy" file litter (Dropbox, Syncthing, READ); handle in place.
10. Virtualise and lazy-load for large trees; numbers are vendor claims only (C9, SEARCH-ONLY).

### Surface D (tabs)
1. Autohide the bar until a second file is open (HIG, READ).
2. Preview tab reused on single click, pinned tabs for kept files (VS Code READ, libadwaita pinned READ).
3. Ctrl+Tab in most-recently-used order and Alt+1..9 (VS Code READ, HIG READ).
4. Overflow: scroll with pinned tabs kept visible (AdwTabBar, READ); an "open files" list as fallback (VS Code, READ).
5. Overview with search for many tabs (AdwTabOverview, READ).
6. Evidence for or against tabs for writers is anecdotal only (D4).

### Surface E (other)
1. Problems: header count, click to jump, inline mark, fix from the top, plain-language wording (VS Code READ, Overleaf SEARCH-ONLY).
2. Search and replace: group by file, preview, deselect before applying (VS Code Refactor Preview, READ).
3. Comments: anchored to a selection, resolve hides but keeps, re-open (Google, READ).
4. Presenter view: current, next, notes, timer (PowerPoint, SEARCH-ONLY).
5. Preferences: search enabled on AdwPreferencesDialog (SEARCH-ONLY).
6. Gaps: export/print, outline, asset insertion, first launch, collaborator notifications, presence in tabs and tree.

### Surface F (others' changes in the text)
1. Presence is ephemeral and kept out of the document; carets disappear when the person goes offline (Yjs awareness, READ).
2. Awareness should be passive, arising from the work itself (Dourish and Bellotti, SEARCH-ONLY abstract); cursors alone are not enough (ADCS 2004, SEARCH-ONLY).
3. Margin change bar with text left clean (Word Simple Markup, READ); light background for inserted text, hover for deleted (Upwelling, READ).
4. Authorship as a toggled overlay with tone per person and stripped on export (iA Writer, READ).
5. Offer a way to hide others' cursors, remembered across sessions (Figma/Miro/Lucid requests, SEARCH-ONLY).
6. Screen-reader users get a live-edits log with name, time and change type, not interrupting speech (Google, SEARCH-ONLY).
7. Caret and flag at 3:1 contrast and never colour alone (WCAG 1.4.11 and 1.4.1, READ).
8. Undo only my own edits (Yjs trackedOrigins, SEARCH-ONLY).
9. Gaps: name-flag timing, off-screen jump chips, caret density limits, fade durations: no source found.
