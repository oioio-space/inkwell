# BK6: C5's truth undercounted lost GSO batches; R2's margin re-derived at 1e-7 per run

Rigour: light (test oracle and tolerance; no product change). Symptom: GitHub run 43920252732 (branch
`candidate/sb2a1-8`, a sandbox-only diff), job netsim, scenario 5 seed 20773. C5 was red on R2 alone: « P1 AB
t=75.887: figure 0.047 outside [0.0283, 0.0466] (T* 0.0363..0.0387) », and the same at 77.887.
`c5model.py verdict` on the run's recorded input (artefact `netsim-traces`, `results/5-s20773-c5.json`) replays it
exactly.

## 1. What the data shows

- **One plateau, one window long.** AB's figure jumps by +0.0076 at t = 50.9 while T* moves by +0.0004. It stays
  +0.005 to +0.0099 above the middle of T*'s range, then falls by 0.0116 at t = 78.9, 28 s later. That is about
  50–60 of A's packets lost without the two netem qdiscs counting them. It is not a crossing, because an endpoint
  error does not last a whole window.
- **A lull just before it.** Both directions go nearly silent for about 1.5 s: AB's first hop forwards 216, 111,
  **10**, 166 and 204 packets in seconds 47–51, and BA reads 98, then **5**. The sampler steps of both peers stay
  1 s apart. The cause of the lull is not established, and it is not attributed to load.
- **Same netem draws, different outcome.** The netem chains are seeded. The local run of the same seed (13:07)
  has the same loss burst on AB's first hop (16 drops in second 49) and its figure stays inside the range. In four
  other recorded runs the figure is centred on T* (means −0.49 to +0.34 and sd 0.27 to 0.69, in units of
  √(T*/n); the model gives sd 0.56), so the figure has no bias.

## 2. Root cause: the truth counted a lost batch as one drop (proven)

quic-go v0.64.1 sends a run of full-size packets as one UDP GSO batch (`connection.go` `sendPacketsWithGSO`,
pacer burst `maxBurstSizePackets = 10`). After a lull, its backlog leaves that way. A veth hands the batch on
whole, so the NAT's netem sees one skb. `netem_enqueue` (`net/sched/sch_netem.c`) draws the loss once per skb and
adds **one** to `dropped`, while `Sent … pkt` counts the segments (`bstats_update` adds `gso_segs`). So a lost
batch of k packets reads as one drop, and T* is biased low. The figure (packets the peer did not receive) was
right.

**Proof.** `topology.sh truth-check`, run in the netsim namespaces: one UDP_SEGMENT send of 10 segments from alice,
then from bob, through a `loss 100%` netem on their NAT's wan egress, with the relay's address pinned on the NAT
so that no ARP request is lost. On the topology of `main`, `dropped` grows by **1** (2 in mesh mode, where
another packet passes): red in cone, symmetric and mesh. With the fix it grows by **10**: green in all three.

**Fix (harness only).** `segment_early` sets `gso_max_segs 1` on every endpoint's own interface (alice eth0 and
eth1, bob, the relay, carol). The kernel then segments a batch in software as it leaves the endpoint, before any
netem, as a Wi-Fi card sends one frame per datagram. The product still makes its GSO syscalls. `ip link set …
gso_max_segs 1` was chosen over `ethtool -K … tx-udp-segmentation off` for three reasons:
- it needs no new tool (iproute2 is already required, and ethtool is not in `run.sh`'s list);
- it works in the user namespace, as measured;
- it also covers TCP segmentation offload, which would undercount the same way.

Both settings gave +10 in the measurement. `run.sh` runs `truth-check` after `topology up` for every impaired
scenario (5–8) and fails the scenario loudly if the counters undercount.

Set aside:
- `QUIC_GO_DISABLE_GSO` changes the product under test.
- Widening R2 to absorb the bias hides an oracle defect, and the bias grows with the batch size.

## 3. R2's margin at a stated false-alarm rate

**Origin of the old number.** `tol = 1.5·√(T*_hi/n) + c/n + lag/(W−2)` dates from 46947f6. `c` and the lag are
derived bounds; the **1.5 was chosen** (« covers the foreign packets ») and only checked: 0 failures in 3000 runs
bounds the rate by 1e-3 at 95 %. In the model it was indeed about 1e-3. Over 3000 runs (seed 29), the honest
prober used up to 1.19 of the margin and failed R2 in one run, at P0>P1, below the truth, where the filler drops
from 360 to 120 packets/s inside the window. Run NI-1 once per CI, ≈ 5000 runs a year, that is a few false
reds a year.

**Derivation** (`c5model.py scale --runs 3000 --seed 29`, `margin_used`, `derive_scales`). The margin of each window
class is scaled by `k`, and a run fails R2 in a class exactly when its largest use there exceeds `k`. The target is
1e-7 false failures per run (BK3's standard), split by Bonferroni over the L = 11 classes. There are three kinds of
class:
- **A phase without loss (P3, P4).** T* = 0, and the figure's error is the crossings plus the permille rounding.
  `c` already bounds the crossings (the largest over 4000 traces, × 1.5). The honest use there is discrete (whole
  permille), so no tail can be fitted: **k = 1**.
- **A phase with loss, and P0>P1 (the change where our rate changes).** The tail of the honest runs' largest use
  is fitted as a generalized Pareto by moments to the top 10 %, its shape floored at 0 (S. Coles, *An Introduction
  to Statistical Modeling of Extreme Values*, Springer 2001, §4; Hosking and Wallis, *Technometrics* 29, 1987). It
  is read at 1e-7/11, and k is the 95 % bootstrap upper bound, rounded up to 0.05: **P0 1.75, P0>P1 2.75,
  P1 1.15, P2 1.05, P5 1.25**.
- **Any other change.** Same rate on both sides; the lag is the derived `transition_lag`. A per-class fit fails
  here: the use mixes an atom and rare lag events, and the fit extrapolated to 3.6–20. So the class takes **the
  larger scale of its two phases**: P1>P2 1.15, P2>P3 1.05, P3>P4 1, P4>P5 1.25.

The extrapolation reads the level six decades past 3000 runs. The bootstrap bound and the floor of the shape at 0
make it conservative. `Scale.test_derived_scale_covers_an_exponential_tail` checks this on ten exponential samples
of 3000: the bound is never below the exact level.

**Power, unchanged.** On the same 3000 runs:

| | honest rejected | old figure | M5b | 60 s window (stale) | every R1 mutant | halved thresholds |
|---|---|---|---|---|---|---|
| C5S margin (k = 1) | 1 | 3000 | 3000 | 3000 | 3000 | 2995 |
| BK6 `RULE.ks` | **0** | 3000 | 3000 | 3000 | 3000 | 2995 |

The R2 mutants are caught where their use stays above the new scales:
- the old figure in P0, using at least 1.83 against 1.75;
- M5b in P3, using at least 2.91 against 1;
- the 60 s window in P3, using at least 1.80 against 1.

A single uniform k cannot do this. At k = 2.2 (1e-7 by a single fit), the 60 s window slips to 2928 / 3000 and the
old figure to 2998.

Independent confirmation: `c5model_test.Statistics` (seed 101, 3000 other runs) with `RULE.ks`: 0 honest rejections (≤ 1e-3 per run at 95 %, all that 3000 runs can show directly) and every required mutant rejected in 3000 of 3000 (power ≥ 0.999).

**What the old margin hid.** The CI failure used 1.04 of P1's margin. The new P1 scale (1.15) would have passed it,
but that is not the fix: the fix is section 2, which removes the cause.
