# BK5 — a "deck" or "anchors" request that arrives while the previous answer is sent is lost

Rigour: light (a product defect in `internal/app` preview scheduling, local to one file; no protocol, no peer bytes).

## Symptom

GitHub run 43920252732, job `sandbox-stock` (`go test -race`): `TestPreviewScheduling/PRV-37 the slides and steps are
answered, and computed once per version` failed; the job log showed only the verdict (`gojson_check` prints no test
output).

## Cause, with evidence

Reproduced on this machine (`-race -count=2000 -failfast`, no added CPU pressure; two other heavy jobs held the other
slot): `preview_test.go:593: no "deck" message` after 60 s, that is the **second** request was never answered.

`Preview.handle` coalesced requests with a flag (`askingDeck`, likewise `asking` for anchors): a request that finds the
flag set returns, expecting "the answer to the running one" to reach the webview. The flag was cleared in a `defer`
**after** `cur.send`. So a request handled between the send and the defer (the webview asks again as soon as an answer
arrives) was dropped, though the answer it relied on was already sent. Two consequences in the product:

- the request is never answered (the deck view waits; an "anchors" jump waits for its timer);
- after an edit, `preview.svelte.ts` asks for the deck on each new result; a request dropped this way leaves the
  previous version's slides on screen, and the flag ignored the version entirely: a request for a newer version was
  coalesced with a computation for an older one.

The suspects of the brief were checked: `Changed` is synchronous (it bumps `srcGen` under the lock), the cache is
written under the lock before the send, and `message` skips other types but cannot pick a stale "deck" (the test reads
each answer before asking again). None causes the observed hang.

## Fix

`answering` (one per kind) replaces the two flags: one computation at a time; a request is coalesced when the running
computation is for the same version of the sources (its stream is added to the ones it answers), otherwise one more
computation follows for the version current when it starts and answers every stream that asked meanwhile. The streams
are sets: two can be live at once, since `Preview.Serve` replaces `p.cur` while Wails still serves the old stream of a
reloaded page until it closes it (`cmd/inkwell/main.go`, `HandleStream`); a single "again" stream would let a later
request overwrite an earlier one's (review point, red arm of PRV-38). The end of a computation (cache, decision, flag) is taken under `Preview.mu`
before its answer is sent, so a request handled during the send starts its own computation (a cache hit for the same
version). `answerAnchors` and `answerDeck` now return the message instead of sending it.

## Proof

- `PRV-38` (new, deterministic): the fake stream sends the next request from inside the delivery of the first answer
  and waits until `Serve` has handled it (it asks for the next frame), for deck and anchors, with and without a change
  in between, plus two live streams where the second is coalesced and the first then asks after a change. Red on the
old code (four "no message" failures) and the two-stream arm red on the single-stream version, green after; it also asserts one computation per
  version and that the deck after a change is of the newer version.
- PRV-36 (flood, one computation) and PRV-37 unchanged and green; PRV-37 2000 runs under `-race`; the whole
  `internal/app` package under `-race`; `mise run lint`.

## Diagnosability (proposal, not applied here)

`scripts/gojson_check.py` is not on `main` yet (it comes with SB2a1). It should print, for each failing test, the
`Output` lines of its `go test -json` events (the `--- FAIL` line and the `file:line:` messages), capped (for example 40
lines per test), so that a CI failure is diagnosable from the job log; to be added in SB2a1's branch with a case in
`gojson_check_test.py`.
