# Formal and systematic checks for the interface (W39, 2026-11-09)

User request (2026-11-09): « Pour l'UX/UI utilises-tu aussi des choses formelles ? » then « Fais tes
recommandations ». Usability itself is measured, not proven (ux-walkthrough: cognitive walkthrough and Nielsen's
heuristics on a fixed rubric). What can be stated as a rule is made executable, the same way as the protocol: a
model, tests generated from it, and mutants that the tests must catch.

## What already exists

- TLA+ state models of what the UI claims (SyncIndicator.tla), linked to the code by fast-check model-based tests
  (block SI1) and mutants.
- Property tests (fast-check) in 12 frontend test files (editor format commands, admission, ...).
- axe-core (WCAG) in 2 of 17 Playwright specs (`sheet`, `shell`).
- ux-walkthrough (agent `ux-tester`) and the light/dark capture comparison before each merge.

## Three rules (engineering-principles.md §5)

### UF-1. Every e2e spec checks accessibility (axe-core)

- One shared fixture in `frontend/e2e/` runs `AxeBuilder` (tags `wcag2a`, `wcag2aa`, `wcag21aa`, `wcag22aa`) after
  each test, on the final page and on every dialog or popover the test opened, and fails on any violation.
- An exception is a named rule plus a justification in one allow-list file, each one with an owner and an expiry
  date, like `gates/guard-overrides.json`.
- Proof: a seeded violation (an `<img>` without `alt`, a button without a name) turns the suite red.
- Source: https://playwright.dev/docs/accessibility-testing and https://github.com/dequelabs/axe-core-npm.

### UF-2. Hit-test invariant: what must be clickable is clickable

- The same fixture checks, after each test step that changes the layout, that every visible, enabled interactive
  element (button, link, input, `[role=button]`, menu items) is the hit target of its own centre:
  `document.elementFromPoint(cx, cy)` is the element or one of its descendants.
- Overlap is allowed only for an open modal layer and what it covers.
- This is W36's C2. The defect it targets is the toolbar laid over « Partager »: the user sees the button but
  cannot click it.
- Proof: a mutant that removes the `overflow: clip` of the toolbar, or that moves an element over a header button,
  must be caught.

### UF-3. Multi-step flows are statecharts, and their tests are generated

- A flow with more than three states is written once as an XState v5 machine (test-only dependency, `xstate`).
  Flows: invitation (create, share, join, admit, refuse, expire), conflict on reopening, reconnection and offline,
  export.
- The machine states the allowed events per state and the visible state.
- `createTestModel(machine).getShortestPaths()` (`xstate/graph`) generates one Playwright path per reachable
  transition, plus `getSimplePaths()` for flows small enough to cover every path.
- Each state carries its assertions: what is shown, what is enabled, and that the other events are not offered.
- The machine is reviewed as the spec of the flow before the UI is changed, the same way as the gates.
- Proof: a mutant per machine (a button enabled in a state where the machine forbids it, a missing transition) is
  caught.
- Sources: https://app.unpkg.com/xstate@5.32.5/files/dist/declarations/src/graph/TestModel.d.ts,
  https://socket.dev/npm/package/playwright-state-model,
  https://dev.to/ryanroselloog/model-based-testing-using-playwright-and-xstate-what-ive-learnt-so-far-4180.
- Why not a home-made walker: the graph traversal (shortest and simple paths, with event payloads) is what the
  library provides, it is maintained, and `xstate` has no runtime dependency.

## Beautiful, practical, simple, friendly, Adwaita (W40, 2026-11-09)

User request: « l'UI/UX doit être top ! Belle, pratique, simple et conviviale, et suivre Adwaita ; une apparence de
simplicité malgré des fonctions évoluées, sans brider l'utilisateur ; regarder les meilleures pratiques et les choses
formelles dans ce sens ». The rules already stand in `docs/ux-principles.md`. The GNOME HIG principles say the same
(https://developer.gnome.org/hig/principles.html): design for people, make it simple (one purpose per view, reveal
complexity gradually), reduce user effort, be considerate (undo rather than confirm). What can be checked by a
machine becomes five more executable rules. Beauty itself stays judged by the ux-walkthrough and the light/dark
captures; UF-8 keeps it from regressing.

### UF-4. Adwaita tokens only

- `docs/ux-principles.md` already says it: components reference semantic tokens, never a raw value. Today 9
  components still hold raw hex colours (Toast, SearchPanel, Grid, PeopleStack, PeopleDialog, Preview, and three in
  present/).
- A lint step in `fe:check` refuses any raw colour (hex, `rgb()`, `hsl()`, named colours) and any raw length outside
  the token files, in `.svelte` and `.css`. The only exceptions are listed, each with a reason (for example, the
  colours of the produced PDF, rule 7).
- Proof: a seeded raw `#fff` turns `fe:check` red.

### UF-5. Effort budgets for the five tasks

- The tasks are create, share, review, present and export (`docs/ux-principles.md`), plus « type and see it on the
  other device ».
- Each task is a scripted Playwright path. The shared fixture counts the person's operators along it: clicks, key
  presses other than the typed text, pointer travel between targets, and waits on the system.
- From those counts it derives a Keystroke-Level Model time, with the operator values of Card, Moran and Newell
  (1980): K 0.28 s, P 1.1 s, H 0.4 s, M 1.35 s. KLM predicts expert time without users
  (https://measuringu.com/?p=343).
- Budgets are frozen in a file. A change that adds a step, or more time, to a task is red unless the budget is
  raised with a reason.
- Proof: a mutant that adds a confirmation step to « share » is caught.

### UF-6. Simple to look at, nothing out of reach

- Simplicity is measured: a budget of visible primary controls per view. The header bar holds the title, the sync
  state, the avatars and at most the budgeted buttons (rule 2, « le texte d'abord »).
- Nothing is restricted: every command of the registry is reachable from the palette, with its shortcut shown, and
  from a menu in at most two steps (rule 3, « trois accès à tout »).
- The test enumerates the command registry, so a new command without a palette entry or without a menu path is red.

### UF-7. Undo rather than confirm

- Every destructive transition of a flow's statechart (UF-3) is followed by an « Annuler » event that restores the
  previous state for the toast's lifetime (rule 6; HIG « be considerate »).
- A machine with a destructive action and no undo is refused by the model test.

### UF-8. The look does not drift

- Every view, in light and dark, has a visual baseline (Playwright `toHaveScreenshot`, fixed fonts and data, motion
  reduced).
- An unintended difference is red. An intended one is accepted with the new baseline and its light/dark comparison
  in the block's UX report.

## Order in the global plan

- Block **UF1** (UF-1, UF-2, UF-4 with the nine components fixed, UF-8; one shared fixture): next after SI1, in the
  lot « Collaborer sans perdre ». It also closes W36 C2.
- Block **UF2** (UF-3, UF-7, and UF-5 on the same paths): the invitation and « share » flows first (the most states,
  and the first thing a new person sees), then the other flows one block each, each one before its next UI change.
- UF-6 goes with the command palette work, or with UF1 if the command registry is already enumerable.
- Each block: frozen gate first (`gates/<bloc>.toml`), seeded mutants, then the code.
